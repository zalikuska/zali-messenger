# Игровой статус («Играет в …») — контракт и инварианты

`./scripts/activity_doctor/run.sh` проверяет веб-половину на боевом
`ZaliInterface` и серверные юнит-тесты; сквозной путь через настоящие сокеты —
`tests/activity.rs`.

## Кто за что отвечает

| Слой | Файл | Роль |
|---|---|---|
| Оболочка macOS | `apps/macos/.../Services/GameDetector.swift` | видит процессы, шлёт `native_game_activity` |
| Оболочка Windows | `apps/windows/src/native/game_detector.rs` | то же + `RunningAppID` Steam |
| Веб | `web/src/interface/game_activity.js` | **единственное** место политики: переключатель, ручной статус, «это не игра», `since`, отправка |
| Сервер | `server/src/activity.rs` | хранит в памяти на соединение, рассылает друзьям и соседям по серверам |

Оболочка ничего не знает о настройках и ничего не шлёт на сервер сама. Веб
включает опрос командой `GAME_DETECTOR_CONFIG {enabled, games}` и получает
ответ realtime-событием `native_game_activity` (тот же проход, что у кадров
сервера — новых каналов в мосте нет). На сервер уходит `client_activity` через
`VOICE_EVENT` (браузер — прямо в сокет).

## Инварианты

- **Выключено по умолчанию.** По статусу видно, чем человек занят прямо сейчас;
  без явного согласия наружу не уходит ничего, и оболочка не опрашивает
  процессы (`GAME_DETECTOR_CONFIG` с `enabled:false` и пустым каталогом).
- **Только однозначные признаки:** имя процесса есть в каталоге; путь внутри
  `steamapps/common/<Игра>`, `Epic Games/<Игра>`, `GOG Games/<Игра>`; Steam
  `RunningAppID` (Windows). **Не возвращать правило «LSApplicationCategoryType =
  games»**: категорию ставят и лаунчерам (Steam, Epic, Modrinth App) — у каждого с
  открытым лаунчером горело бы «Играет в Steam». Проверено на живой машине
  2026-10-11.
- **Каталог — один, в `game_activity.js` (`gameCatalog()`).** Уходит оболочке при
  включении. Ключи — имя процесса в нижнем регистре без `.exe`. Нет `java`/`javaw`:
  под ними живёт что угодно.
- **Один процесс — несколько игр различается `path`.** Необязательное поле записи
  каталога — подстрока пути к exe (без регистра, `/` = `\`). Пример: osu! stable
  (`\osu!\`) и osu!lazer (`osulazer`) — оба `osu!.exe`. Запись с `path` без
  известного пути не срабатывает (не гадаем), а оболочка для таких процессов
  запрашивает путь (`is_path_constrained` в Windows). Deadlock — `deadlock.exe` (старое кодовое имя `project8` оставлено для прежних установок).
- **Наружу — только название и источник, не список процессов.**
- **Сервер не доверяет полям:** название чистится от управляющих символов и
  режется до 64 символов, `source` — из белого списка, `since` из будущего или
  старше недели заменяется «сейчас». Клиент экранирует (`esc`) независимо.
- **Статус живёт в `ConnectionPresence.activity`** и исчезает вместе с сокетом —
  ни БД, ни TTL. Аккаунт = самая свежая запись среди его соединений.
- **Рассылка только по изменению** (сравнение «до/после» по аккаунту). Клиент
  повторяет статус раз в 25 с как страховку после реконнекта/рестарта сервера —
  без сравнения каждое повторение стало бы рассылкой на всех друзей. Смена чаще
  раза в 2 с с одного соединения отбрасывается.
- **Зритель — друг или участник общего сервера** (`related_users`, симметрично).
  Рассылка режется `MAX_VIEWERS` (2000).
- **`client_activity` не пишется в лог звонков** ни в macOS (`WebView.swift`,
  case `.voiceEvent`), ни в Windows (`VoiceEvent` в `native.rs`) — иначе строка
  каждые 25 с в журнале интерфейса.
- Повторы шлются только при `S.wsOn`: у голосовой очереди оболочки есть потолок
  (`VOICE_PENDING_MAX` = 64), копить в ней одинаковые кадры незачем.

## Пары (CLAUDE.md)

- macOS Swift ↔ Windows Rust: детектор есть в обоих; платформенные правила
  (Steam-реестр) только в Windows. Экспериментальный macOS Rust-шелл процессы не
  опрашивает (`gameActivity` там не объявляется).
- **Android не реализован:** нужен `UsageStatsManager` + специальное разрешение.
  Чужие статусы Android показывает (общий веб), `GAME_DETECTOR_CONFIG` ему не
  шлётся, пока `supports.gameActivity` нет; ручной статус работает.
- Сервер: правка `activity.rs`/`realtime.rs`/`push.rs` нужна и в `zali-server`
  (пуш + деплой — скилл `zali-ops-deploy`); сервер выкатывается раньше клиента.
  Старый сервер просто молча игнорирует `client_activity` (тип неизвестен).

## Режим «в игре» (отложенные и тихие уведомления)

Получатель в игре выбирает: уведомления приходят как обычно / **откладываются до
конца игровой сессии** (`defer`) / приходят **без звука** (`silent`); для кого —
всем, только друзьям, только выбранным, всем кроме выбранных, никому; в каких
играх — пустой список = в любой. Файлы: `server/src/focus.rs` (настройки в таблице
`game_focus_settings`, решение, события, `POST /api/message/:id/notify-now`),
`web/src/interface/game_focus.js` (настройки, очередь, заметка отправителя),
точка применения на клиенте — `notifyBackgroundMessage` → `presentMessageNotification`
в `notifications.js`.

- **Откладывается уведомление, не сообщение.** Сквозная переписка: сервер
  доставляет сообщение сразу, у получателя оно в чате и в счётчике. Меняются
  только тост, сигнал и пуш.
- **Решает сервер** (`decide`): он один знает игру получателя, дружбу и
  настройки. Политика уходит клиенту событием `notify_policy` **до** самого
  сообщения — по одному соединению порядок сохраняется (проверяется
  `tests/focus.rs`). Отправителю — `delivery_note` **без названия игры**.
- **Сырой статус игры отделён от показываемого.** Клиент шлёт `client_activity`
  и когда статус никому не показывается, с `share:false`: серверу игра нужна для
  режима, а рассылается только то, что `shared` (`public_activity`). Поэтому
  включённый режим включает определение игры, даже если «Показывать, во что я
  играю» выключено (`effectiveGameActivity`, `gameFocusEnabled`).
- **Конец сессии — с задержкой** (`FLUSH_GRACE` 20 с, в тестах
  `ZALI_FOCUS_FLUSH_GRACE_MS`): перезапуск лаунчера — одна сессия. По окончании —
  один сводный пуш на отправителя и `focus_flush`; у клиента есть резервный
  таймер 45 с на случай потерянного кадра.
- **«Всё равно оповестить»** работает, пока сообщение в `focus_pending`, и
  только у его отправителя; повтор и чужие вызовы — 404. Пуш при этом помечен
  `force`: service worker и Android иначе приняли бы его за повтор тихого.
- **`silent` в разных оболочках:** web — `showNotification({silent})` (при
  `silent` нельзя `renotify`, иначе TypeError); macOS — `content.sound = nil` и
  `.passive`; Android — `setSilent`; Windows — тост и так без звука (`notify-rust`
  без `sound_name`), поэтому достаточно не играть сигнал в вебе.
- **Отложенное видно как кружок на значке, а не как уведомление.** Пока `defer`
  держит тост и сигнал, счётчик непрочитанного уходит на значок приложения тем же
  `syncTaskbarBadge`: Windows — оверлей на панели задач, macOS — `dockTile` (с
  режима «в игре» бейдж в Dock показывает все непрочитанные, как оверлей в
  Windows), установленный PWA — `navigator.setAppBadge`. **Android** рисует кружок
  лаунчер и только по уведомлению, поэтому на время отсрочки ставится тихое
  (канал `zali-quiet`, LOW, `setSilent`) по одному на отправителя
  (`SHOW_NOTIFICATION` с `quiet`/`clear`, `MessageNotifier.showQuiet`). Прочитанная
  переписка снимает и отложенное (`syncFocusHeldWithUnread`), и тихое.
- **Только личные сообщения.** Каналы серверов режим не трогает.
- **Не переживает рестарт сервера** — теряется только отсрочка пуша, сообщения
  лежат в чате.
