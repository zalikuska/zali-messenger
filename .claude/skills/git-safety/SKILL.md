# Git Safety — уроки реального инцидента с потерей кода

**Инцидент** (пути ниже — в структуре до реорганизации 2026-07-12; см. новые
пути в `CLAUDE.md` → Project Structure): `git checkout -f <branch>` +
`git pull --ff-only` между двумя ветками с *разным набором отслеживаемых
путей* удалили с диска реально нужные файлы — `Core/src/*.rs`,
`ZaliArchiverSDK/Rust/src/lib.rs`, `ZaliArchiverSDK/Swift/`,
`macOS/Sources/ZaliMessenger/{NetworkService,ZaliArc,ZaliCore,ContentView}.swift`,
`Package.swift`, `Web/src/{bus,loader,styler,bootstrap}.js`, `Web/index.html`,
`Web/style.css`, `bundle_web.py`, `run_macos_app.sh` и другие build-скрипты.
Причина: `Core/`, `Web/`, `Windows/`, `macOS/`, `ZaliArchiverSDK/` в этом репо
на разных ветках то отслеживались git, то были в `.gitignore` как «legacy,
хранится только в рабочей копии» — то есть их реальный актуальный код
существовал **только на диске**, никогда не коммитился. `git checkout -f` без
раздумий подменяет такие файлы версией из целевой ветки; `pull --ff-only`
после этого удаляет всё, что в новом дереве не отслеживается вовсе.

## Что делать до `git checkout -f` / `reset --hard` / `pull --ff-only` между ветками

1. **Сначала сравнить наборы отслеживаемых путей**, не только диффы содержимого:
   ```bash
   diff <(git ls-tree -r <branch_a> --name-only | sort) <(git ls-tree -r <branch_b> --name-only | sort)
   ```
   Если списки сильно расходятся (особенно если пропадают целые директории
   типа `Core/`, `macOS/Sources/`) — сигнал, что одна из веток не отслеживает
   то, что реально нужно на диске. `git status`/`git diff` этого не покажут —
   они смотрят только на текущий working tree.
2. Никогда не считать `main` «полной» версией проекта только потому, что так
   называется. Проверять `git log --oneline <branch> | tail`, чтобы понять
   реальную родословную (в этом репо было два разных «Initial commit» —
   следствие squash/subtree-операций в прошлом).
3. Секция вида `# Legacy ... kept only in the workspace` в `.gitignore` —
   красный флаг: эти пути живут только на диске, git о них ничего не знает, и
   любая операция, переключающая ветки/делающая fast-forward, может их
   стереть без предупреждения.
4. Если всё же нужно переключиться — сначала `git stash -u` (включая
   untracked) или скопировать директорию целиком, а не надеяться, что git
   сохранит нетрекаемые файлы.

## Где искать материал для восстановления, если файлы всё же пропали

1. **`.claude/worktrees/agent-*/`** — параллельные воркчтри фоновых агентов
   могли быть на другом коммите и не затронуты катастрофой. `git worktree
   list` + сравнить содержимое.
2. **Zip-архивы дистрибуции** (см. скилл `windows-build-distribution`) —
   `zali-windows-source.zip` и подобные экспорты в корне репо или
   `~/Downloads` — снапшоты рабочего дерева на конкретную дату. Проверять
   `unzip -l`, дату модификации и **сверять SHA1** (`shasum`) прежде чем
   считать находку новой информацией. Windows-source zip **не включает**
   `macOS/`, `src/main.rs`, `ZaliArchiverSDK/Swift/` (эти zip датированы до
   реорганизации 2026-07-12) — для macOS-файлов нужен архив вида
   `*-full-code.zip`/`*-all-code.zip`/`*-full-current-code.zip`.
3. **Перебор git-объектов** (`git fsck --unreachable`) может найти висячие
   blob'ы от старых коммитов/сбросов — для больших репозиториев поштучный
   `git cat-file -p` на каждый хэш непрактично медленный, использовать один
   процесс `git cat-file --batch` с потоковым чтением через небольшой
   Python-скрипт.
4. **Кросс-сверка с другим клиентом**: Windows (`apps/windows/src/native.rs`)
   и macOS реализуют одну и ту же логику параллельно. Если один клиент
   пострадал, а другой цел и реально свежий (проверить по `git log`/датам
   файлов, не предполагать) — можно восстановить логику по образцу через
   `graphify query`/явное построчное сравнение, но не копировать бездумно:
   платформенные различия (macOS Keychain vs Windows `keyring`) означают, что
   порт требует адаптации, не 1:1 копирования.

## Как проверять восстановленный/реконструированный код

- Пересобирать и читать реальные ошибки компилятора как чек-лист
  недостающих сигнатур — не пытаться угадать всё сразу. `swift build`/
  `cargo build` даёт точный список того, что реально используется вызывающим
  кодом, и это надёжнее реконструкции «по памяти».
- graphify-граф (`graphify-out/graph.json`) хранит только структуру (какая
  функция существовала, на какой строке, что вызывала), не тела функций —
  полезен, чтобы понять, что *должно* существовать, но не для восстановления
  реализации 1:1.
- `bundle_web.py` — сам по себе генерируемый/поддерживаемый код, который
  может незаметно деградировать (в этом инциденте восстановленная версия
  знала только про 5 JS-модулей вместо реальных 13). После восстановления
  любого build-скрипта — запустить его и проверить, что вывод (счётчики
  файлов, сгенерированные артефакты) соответствует ожиданиям, а не просто
  «скрипт не упал».
- Финальная проверка любого клиентского фикса — реально собрать
  `.app`/бинарник и запустить (`open ZaliMessenger.app` + `ps aux` + проверка,
  что процесс не упал), а не только «компилируется».
