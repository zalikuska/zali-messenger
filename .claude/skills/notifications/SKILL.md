# Уведомления — инварианты, которые нельзя терять

`./scripts/notify_doctor/run.sh` проверяет веб-половину на боевом
`ZaliInterface`. Решение «показывать ли уведомление» принимает веб
(`notifyBackgroundMessage` → `SHOW_NOTIFICATION`) — почти все поломки
уведомлений это поломки веба или того, как нативный слой кормит его историей.
Разбор 2026-09-13 нашёл пять причин, накладывавшихся друг на друга и дававших
«работает через раз»:

- **«Чат на экране» ≠ «пользователь смотрит».** `isDmChatVisible`/
  `isServerChatVisible` — вопрос вёрстки, гейтят отрисовку и сброс счётчика.
  Уведомление гейтится `isDmChatAttended`/`isServerChatAttended` (плюс
  `isAppAttended()`: видимость документа и `document.hasFocus()`, в мобильной
  раскладке — только видимость). Раньше открытый чат глушил уведомление,
  звук и счётчик и при свёрнутом окне. `clearAttendedConversationUnread()`
  снимает накопленный в открытом чате счётчик на `visibilitychange`/`focus`.
  - **Фокус сообщает шелл** (`window.__zaliNativeAppFocus` +
    `onNativeAppFocusChange`): macOS — `windowDidBecomeKey/ResignKey`,
    активация приложения, сворачивание; Android — `onStart`/`onStop`
    (вебвью без `onPause` в фоне остаётся «видимым»); Windows — опрос
    `GetForegroundWindow` раз в 0,5 с (`spawn_windows_focus_watcher`). На
    Windows это и была поломка: открытое, но не активное окно с открытым
    чатом молчало, потому что `document.hasFocus()` внутри WebView2 оставался
    `true`. Не заменять опрос на `WindowEvent::Focused`: `tao` шлёт
    `Focused(false)`, когда фокус уходит внутрь WebView2, а при Alt+Tab из
    вебвью не шлёт ничего.
  - `hasFocus()` не спрашивается только на сенсорном устройстве
    (`isHandheldDevice`), а не в мобильной *раскладке* — узкое окно на
    компьютере считалось «смотрят» при любом фокусе.
- **Перезагрузка истории отменяет только загрузку ТОЙ ЖЕ переписки.**
  Догрузка после обрыва WS шлёт `REFRESH_HISTORY`/`LOAD_SERVER_HISTORY`
  пачкой, по одной на контакт и канал. Один токен на все переписки (macOS
  `WebView.swift`, Android `NativeBridge.kt` — там ещё и общий для личных и
  каналов) пропускал только последнюю: сообщения за время обрыва не давали
  ни уведомления, ни счётчика. Токены теперь по ключу переписки; число
  одновременных загрузок ограничено гейтом (macOS 2, Android 1, LIFO —
  открытый чат не ждёт хвост догрузки). Windows запускает загрузки независимо
  и этим не болел.
- **`loadHistory` устаревает по собеседнику, а не по вызову**
  (`_historyLoadSeqByPeer`) — иначе вызов для второго контакта обрывал разбор
  первого.
- **Разбор истории не ждёт кадров в скрытом документе.** Свёрнутому окну,
  окну в трее и фоновой вкладке `requestAnimationFrame` не дают вовсе:
  продолжение (`scheduleHistorySlice`) страхуется таймером.
- **macOS: заблокированный/погасший экран — «не в фокусе»** (`screenLocked` в
  `syncWebAppFocus`): приложение остаётся активным с ключевым окном, и открытый
  чат глушил уведомление, которое увидели бы на экране блокировки.
- **macOS: закрытие окна не завершает приложение** (`windowShouldClose`
  прячет окно, клик по уведомлению и Dock возвращают). Выход по красной
  кнопке выключал уведомления целиком. Rust-шелл на macOS (экспериментальный)
  по-прежнему выходит.
- **Windows: AUMID регистрируется самим приложением**
  (`HKCU\Software\Classes\AppUserModelId\com.zali.messenger`). Без регистрации
  тост неупакованного приложения молча отбрасывается; до этого AUMID
  регистрировал только ярлык установщика — у запускавших `.exe` напрямую
  уведомлений не было. На живой Windows не проверялось.

## Web Push решается по устройству, а не по «есть ли у пользователя сокет»

`server/src/push.rs::push_suppressed_for`. Раньше пуш уходил только если у
пользователя **ноль** живых WS: открытое приложение на Mac, полуоткрытый сокет
или замороженная фоновая вкладка на телефоне (сетевой стек отвечает на Ping,
JS стоит) глушили пуш на всех устройствах. Теперь:
- подписка хранит `device_id` (тот же, что `X-Zali-Device-ID`);
- вкладка шлёт по своему сокету `client_presence {attended, deviceId}` при
  открытии, `visibilitychange`, `focus`/`blur` и `pagehide` (`web_push.js`);
- сервер держит это на соединении (`AppState.push_presence`) вместе со
  временем последнего входящего кадра; «смотрю» старше 60 с не в счёт;
- пуш не уходит только в подписку устройства, где сейчас смотрят в
  приложение. Подписка без `device_id` (старый клиент) живёт по прежнему правилу.

**Одно сообщение — одно уведомление.** Живая, но не активная вкладка получает
и пуш, и локальное уведомление. У обоих общий `tag` переписки
(`zali:dm:<sender>` / `zali:<sid>:<cid>`) и `messageId` в `data`; второе
молчит — страница его не показывает, service worker переподнимает молча
(`userVisibleOnly` не позволяет не показать). Клик по уведомлению ведёт в
переписку (`notificationclick` → `postMessage` или `?open=`); выход из
аккаунта снимает подписку браузера (`unsubscribeWebPush`). Проверяется
`notify_doctor` (`check_service_worker.mjs`) и юнит-тестами `push.rs`.

## Маршрут по активности: только на устройства, где человек что-то делал

`server/src/device_activity.rs`. Устройство активно, если на нём что-то делали
меньше 2 минут назад (`ACTIVE_WINDOW_SECS`). Есть активные — уведомление (пуш
и локальное) только на них; бездельничают все — на все.
- **Кто меряет.** `client_idle {deviceId, idleSeconds}` по WS. macOS
  (`DeviceIdleWatcher.swift`, `CGEventSource`) и Windows
  (`spawn_windows_idle_reporter`, `GetLastInputInfo`) — **системный** простой
  из натива, не из вебвью: свёрнутое окно мыши не видит, таймеры вебвью режут.
  Android — `MainActivity.dispatchTouchEvent` + `onStart`/`onStop`
  (`NativeBridge.noteUserActivity`): свернул/закрыл — тоже действие. Браузер —
  своими событиями ввода/видимости (`device_activity.js`); в нативных шеллах
  вебвью **не** шлёт. Пока активен — раз в 30 с, перестал — тишина.
- **Сервер** хранит момент последнего действия по (логин, устройство) в памяти
  и в таблице `device_activity`; назад время не идёт. Простой в целых минутах
  вниз — `GET /api/devices/activity`.
- **Достижимость.** Активное устройство — адресат, только если у него живой
  сокет со входящим кадром за 45 с или пуш-канал. Иначе закрытая крышка
  ноутбука две минуты глушила бы телефон.
- **Единственное исключение — чат открыт прямо сейчас.** Веб (со всех
  платформ, через `sendClientActivityFrame`) шлёт `client_view {conversation}`:
  ключ `dm:<собеседник>` / `<сервер>:<канал>` — тот же, что `tag` уведомления
  без `zali:` (`PushNotification::conversation`). Только когда чат на экране и
  окно в фокусе; повтор раз в 25 с, сервер держит отметку 60 с. Если чат открыт
  на **активном** устройстве — пустой маршрут: ни пуша, ни системного
  уведомления нигде. Чат, оставленный открытым на брошенном компьютере, телефон
  не глушит. `client_presence attended=false` (Android `onStop`) снимает
  открытый чат со всех сокетов устройства — замёрзший вебвью сам не скажет.
- **Клиенту** — `notify_route {messageId, devices}` раньше сообщения, только
  когда уведомлять не все. Не в списке — только счётчик
  (`notifyRouteAllows`). Без маршрута (догрузка истории, свой id неизвестен) —
  уведомлять. `send_push_routed` берёт тот же маршрут.
- Web Push и FCM шлются **параллельно** (`tokio::join!`), подписки и токены
  внутри — тоже: раньше FCM ждал все веб-пуши (DNS + HTTP до 10 с каждая).

## Нативный Android — FCM

`server/src/fcm.rs`, `PushMessagingService.kt`: то же решение по устройству
(`fcm_tokens.device_id` + `client_presence` с нативного WS), тот же
`PushNotification` (`native_data`). `send_push` шлёт по обоим каналам сразу.
Включается `FCM_SERVICE_ACCOUNT_FILE`; OAuth-токен кэшируется на час, мёртвые
токены (404, UNREGISTERED, SENDER_ID_MISMATCH) удаляются, временные ошибки —
нет.

## Не закрыто

Фоновой доставки в нативном iOS нет (ни APNs); сервер не знает о заглушённых
чатах — пуш по заглушённому чату придёт; первое сообщение от нового
собеседника, пришедшее раньше ключа, догружается историей без уведомления
(`peerAlreadyPrimed`).
