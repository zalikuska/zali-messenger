# Производительность — инварианты, которые нельзя терять

`./scripts/perf_doctor/run.sh` проверяет их на боевом `ZaliInterface`.
Запускать после правок в отрисовке списка сообщений, во вложениях, в
аватарах и в персисте кэша.

Общий принцип: **цена действия пропорциональна действию, а не размеру всего,
что уже накоплено в переписке.**

## Двоичные данные не попадают в текстовые пути

Нативные шеллы отдают вложения и аватары в вебвью как `data:`-URL
(`WebView.swift::makeDataURL`, `native/util.rs::make_data_url`). Такой payload
обязан быть переведён в `blob:`-ссылку до попадания в разметку:
- вложения — `attachmentDisplayUrl()`, только из `renderAttachmentPreview()`.
  Не переносить вызов в `normalizeAttachment()`: её зовёт ещё и
  `saveStoredMessageCache()`, обходящий вложения **всех** переписок;
- аватары — `saveStoredAvatar()`, единственная точка входа в `avatarCache`.

До 2026-09-05 этого не было: кадр списка на диалоге из 60 сообщений с 6 МБ
фото занимал 10,5 МБ строки при 1070 символах текста, из них 2,5 МБ — тридцать
копий одного аватара; вся строка проходила через `esc()` (пять regex-проходов
= 52 МБ сканирования) и оседала второй копией в `_lastMessagesHTML`.

**Ссылка в разметке больше не является полезной нагрузкой.** Нативному мосту
сохранения (`DOWNLOAD_ATTACHMENT`) нужен именно payload — обратный поиск живёт
в `_attachmentBlobPayloads`, используется в `downloadAttachmentFromHref()`.
Сломать = молча свалиться в браузерный путь `<a download>`, который WKWebView
и WebView2 не исполняют.

## Персист кэша сообщений

- **Детектор изменений — сериализация БЕЗ payload-ов.** Байты вложения
  неизменны: сообщение с другим набором вложений — это другое сообщение, с
  другими id и размерами. Полный `JSON.stringify` архива ради сравнения стоил
  ~9 мс на каждое сохранение, включая те, что ничего не меняют.
- **В `localStorage` payload-ы пишутся только там, где их больше негде
  хранить** (`messageCachePayloadsHeldElsewhere()`): на macOS есть нативный
  кэш-файл (`saveMessageCache`), в браузере `blob:`-ссылка всё равно мертва
  после перезагрузки. Windows/iOS/Android нативного кэша не имеют — там
  payload-ы хранятся, пока влезают в квоту.
- **Отказ по квоте фиксируется против той строки, на которой произошёл.**
  Раньше `catch` сбрасывал `_lastSavedMessageCacheJson = null`, каждое
  следующее сообщение заново пересобирало весь архив и падало.
- **`saveInjectedMessageCache()` кладёт объект, а не строку** —
  `loadInjectedMessageCache()` принимает оба вида.
- **`adoptAttachmentPayloads()`** — единственное, что берётся из входящей
  копии при сверке собственного отправленного сообщения. Без него после
  перезагрузки свои же фотографии навсегда оставались чипом с именем файла.

## Путь отправки

Между Enter и появлением пузырька не должно быть ни одного `await`, когда
ключ разговора уже есть на устройстве: `getStoredConversationKey()`
синхронный, `resolveConversationCryptoKey()` вызывается без ожидания ради
своих побочных эффектов. Сохранение кэша на этом пути — только
`scheduleSaveStoredMessageCache()`.

## Отрисовка

- `esc()` — один проход по строке, а не пять.
- `normalizeAttachments()` мемоизируется на массиве-источнике и
  инвалидируется по идентичности объектов и payload-строк.
- Видео: `autoplay loop muted` — только для гифкоподобных вложений,
  `IntersectionObserver` обязан симметрично ставить на паузу за экраном
  (эталон — `modules/tgs.js`).
- Отчёты о неудачной расшифровке уходят из кадра отрисовки через
  `queueDecryptFailureReport()`; вся пачка делит один запрос
  `fetchCanonicalKeyIds(..., { allowCached: true })`.
- Мобильный `backdrop-filter` вынесен в токен `--m-glass` и снимается на время
  жеста (`body.mobile-nav-dragging`); `will-change: transform` ставится
  только на время жеста.
- **Иллюстрации (`--decor`, `mask` с вложенным SVG) — только через тумблер**
  `body[data-decor-art]` (`zali_decor_art_v1`, `prefs.js: applyDecorArt`). На
  Android по умолчанию выключены: Хаб ↔ ZaliCoin с ними — 70–93% рывков кадров,
  без них 6–19% (gfxinfo). Новый декор через `mask`/`filter` с SVG — не добавлять
  без замера на телефоне; `will-change` на нём помог лишь до 32%.
- **Чтение анимируемых значений в Compose — внутри лямбд** (`offset {}`,
  `graphicsLayer {}`, `drawWithContent {}`), не в теле композиции: иначе пружина
  капсулы нативной панели перекомпонует её на каждом кадре.
- **`syncMobileDockThumb()` не читает геометрию на нативных шеллах**
  (`nativeSupports('mobileNav')`): `offsetWidth` скрытого веб-дока — это
  синхронная раскладка всей страницы в клике (~40 мс на вкладку).
- **На Android-оболочке размытия нет вовсе** (`html.is-android-shell`, класс
  ставит `NativeBridge.documentStartScript`; правила — рядом с
  `body.mobile-nav-dragging` в `web/style.css`). Живой разбор DOM (CDP) на экране
  списка показал три вложенных `backdrop-filter`, из них один — полноэкранный
  `.sidebar` поверх собственного непрозрачного фона, то есть размывать нечего.
  Шапки/поле ввода на Android — сплошной `var(--bg)`. Новая поверхность с
  `backdrop-filter` на мобильной раскладке = через `var(--m-glass)`, а не
  литералом. Проверка: `document.querySelectorAll('*')` с
  `getComputedStyle(e).backdropFilter !== 'none'` на устройстве.

## Событие стоит одну строку, а не весь список (2026-09-22)

`check_incremental_render.mjs` в perf_doctor. Замер в браузере на аккаунте со
150 чатами до правок: приём одного сообщения ~13 мс JS + ~7 мс раскладки,
холостой кадр списка из 78 пузырей 6,5 мс.

- **Список сообщений и сайдбар контактов собираются из строк** (одна строка
  разметки = ровно один элемент верхнего уровня) и применяются через
  `patchListRows()` (`render_shell.js`): неизменившиеся узлы остаются, новые
  разбираются одним `<template>`. Сайдбар — `commitListRows()`, список —
  прямой вызов из `_renderMessagesNow()`. Не склеивать два элемента в одну
  строку и не возвращать `innerHTML = html` целиком: сопоставление строк
  узлам сломается, и каждое событие снова пересоздаст все пузыри с их
  `<img>/<video>`. Внешняя запись в `#msgs` (пустое состояние, голосовой
  канал) распознаётся поузловой сверкой — отдельный флаг не нужен.
- **Даты — только через `fmtTime()`/`fmtDate()`** (`format.js`): форматтеры
  `Intl.DateTimeFormat` создаются один раз, результат запоминается по метке.
  `toLocale*String('ru-RU', {...})` строит ICU-форматтер на каждый вызов — это
  было 5 из 5,8 мс кадра. Сравнение имён — `compareContactNames()`
  (кэшированный `Intl.Collator`), не `localeCompare(…, 'ru', {...})`.
- **`addLogEntry()` не трогает DOM синхронно** — строки журнала уходят в
  `#logBody` пачкой за кадр (`flushLogEntries()`). Прямая вставка читала
  `scrollHeight` сразу после чужих правок DOM: 9 мс принудительной раскладки
  на каждое входящее сообщение. Кто читает журнал из DOM — сначала
  `flushLogEntries()`.
- **`loadStoredConversationKeys()` запоминается** против сырых строк обоих
  хранилищ и ссылки на внедрённую карту; наружу — копия. ~30 вызовов на
  путях отрисовки и отправки больше не разбирают JSON каждый раз.
- **`conversationLastMessageAt()` запоминается** по ссылкам хвостовых
  сообщений (сообщения не мутируются на месте по `timestamp`).
- **Свип переотправки ключей спрашивает справочник устройств один раз на
  пользователя** (`deviceDirectory` из `_retryPublishConversationKeysImpl`).
  Остальные пути публикации его не передают и спрашивают свежий список —
  иначе новое устройство не получит ключ до следующего свипа.

## История: архивы в ответе, а не запрос на строку (2026-10-10)

`GET /api/messages/:user` и `…/channels/:id/messages` с `inlineArchives=true`
кладут архивы ≤32 КиБ прямо в строку (`inlineArchive`, base64), бюджет —
1 МиБ на страницу (`HISTORY_INLINE_BUDGET_BYTES`, server/src/messages.rs).
Без этого перезагрузка истории = запрос страницы + отдельный
`GET /api/download/:id` на каждую строку (на Android — ещё и строго
последовательно). Все четыре клиента просят вложение **только при первой
загрузке разговора** (`takeHistoryInlineArchives` в вебе, WebView.swift,
native/cache.rs, NativeBridge.kt): кэш расшифрованных живёт в памяти, дальше
строки берутся из него, и байты гонялись бы впустую. Неудачная загрузка
отдаёт право обратно; сброс кэша расшифрованных сбрасывает и его. Маршруты
веба — `web/src/modules/api_routes.js` (копия в `interface.js` — запасная).

## Страховочный опрос открытого чата

Браузер без нативного WS опрашивает открытый чат раз в 15 с **только пока
сокет лежит** (`S.wsOn`); при живом — раз в 2 мин
(`scheduleConversationSyncPolling`, пересчёт в `setConnectionStatus`).
Пропущенное за обрыв подтягивает догонялка при переподключении. Раньше было
8 запросов в минуту простоя (история + POST claim).

## Хранилище кэша сообщений на macOS

С 2026-09-22 — файл `~/Library/Application Support/ZaliMessenger/MessageCache/<ключ>.json`
(`NetworkService.writeMessageCache`/`loadMessageCache`), запись на отдельной
очереди `messageCacheIOQueue`. Раньше — UserDefaults: на живой машине plist
домена дорос до 26 МБ, и каждое сохранение переписывало его целиком. Старая
копия переносится в файл при первом чтении и удаляется из UserDefaults.
Непригодный к кодированию payload больше не затирает кэш пустым.

## Постоянный кеш ассетов (IndexedDB)

Аватарки и ассеты серверов кешируются на диске (`web/src/interface/cache.js`), с политикой
вытеснения и прогревом. Правишь `cache.js`, `loadStoredAvatar`/`loadServerAsset` или настройки
кеша — прочитай целиком `.claude/skills/performance/asset-cache.md`: там инварианты, на которых
уже ломались (прогрев не засчитывает обращения, memo на открытии базы, запись по одной).

## Запуск не ждёт сервер (2026-10-15)

`bootstrapSession()` входит в приложение сразу по сохранённой (не просроченной) сессии,
а `GET /api/auth/me` проверяет в фоне (`revalidateBootSession`, `auth.js`). Раньше он
`await`-ил `restoreSession()` с таймаутом `SESSION_RESTORE_TIMEOUT_MS` (12 с) под
экраном-заставкой: при медленном или недоступном сервере каждый запуск был
12-секундным «зависанием» (лог: `restoreSession failed … The request timed out`).
Не возвращать `await` сетевого вызова перед `hideBootSplash()`. Отказ сервера (401/403)
по-прежнему возвращает на форму входа — просто на секунду позже; недоступность
сервера сессию не сбрасывает. Все шаги фоновой проверки сверяют токен с текущим
(`stillCurrent`) — выход или смена аккаунта посреди проверки её отменяют.
