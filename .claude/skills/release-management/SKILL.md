# Публикация релиза

Пошаговые команды и чеклист — в `ops/RELEASE.md` (не в git). Здесь — архитектурные
факты и ловушки, на которых уже спотыкались; без них шаги из `ops/RELEASE.md`
можно выполнить и всё равно сломать релиз.

## Схема версий

`MAJOR.MINOR{a|b|r}BUILD`, например `0.2b9` — буква канала (alpha/beta/release),
ранг `r > b > a` при равных `MAJOR.MINOR`. `compareVersions()` в `interface.js`
также принимает legacy plain dotted версии (старое `1.1.3` в `app_releases`) и
считает их release-каналом.

**Миграция схемы версий (завершена 2026-07-28).** Обе платформы выпустили
переходный релиз под legacy-номером `1.1.4`, чтобы старые клиенты (сравнивающие
версии простым делением по точкам) увидели численный бамп и обновились —
внутри это была сборка `0.2b9`. `checkForAppUpdate()` игнорирует такую запись у
клиентов, уже понимающих новую схему (`VERSION_SCHEME_MIGRATION_CUTOFF_UNIX`,
2026-08-01). С 2026-07-28 обе платформы — в новой схеме.

Плата, принятая осознанно: клиенты на `1.1.3` и старше сравнивают `0.2bN`
старым кодом (`0 < 1`) и больше не видят обновление — их нужно доставлять
руками. Для macOS не было альтернативы: cutoff-логика заставляет **любой**
plain-numeric релиз, опубликованный до 2026-08-01, считаться тем же переходным
бампом и молча игнорироваться — то есть `1.1.5` не увидел бы никто, кто уже
перешёл. После cutoff это ограничение снято само.

Cargo требует строгий SemVer, поэтому `apps/windows/Cargo.toml`'s `version` —
отдельное скучное значение, бампается только чтобы `cargo build` был доволен.
Реальная сравниваемая версия — `APP_DISPLAY_VERSION` в `apps/windows/src/native.rs`.
На macOS такого разделения нет: `APP_VERSION` в `scripts/build_app.sh` идёт
прямо в `CFBundleShortVersionString`.

## Порядок: сервер раньше клиента

Если релиз меняет протокол (новое поле в JS и в хендлере сервера), **сначала
деплой сервера, потом публикация клиента**. Старый сервер игнорирует
незнакомые поля, а старый клиент не умеет пользоваться новыми — совместимость
держится только в эту сторону. Пример: `keepalive: true` в `voice_join`;
старый сервер обработает его как обычный заход в комнату и каждые 8 с будет
рассылать состояние, выбивая второе устройство аккаунта из другой комнаты.
Деплой сервера: `git push serverrepo main:zali-server`, затем pull/build/
`systemctl restart` на VPS и проверка `readlink -f /proc/$(pidof zali_server)/exe`
(команды — приватный скилл `zali-ops-deploy`, `ops/RELEASE.md` §1).

## Шаги (кратко; команды — `ops/RELEASE.md`)

1. Бамп версии во всех местах: `python3 scripts/bump_version.py <версия>`, затем `--check`
   (список мест — `CLAUDE.md` → «Коммиты и пуши»).
2. Сборка клиента(ов) — `./scripts/build_app.sh` (macOS),
   `scripts/build_windows_app.ps1` или кросс-сборка с macOS (скилл
   `windows-build-distribution`). macOS `.app` паковать `ditto -c -k --keepParent`
   — апдейтер распаковывает архив тем же `ditto` и ищет `.app` внутри. Windows —
   голый `.exe`, без архива.
3. Загрузить артефакт в `releases/` дата-директории сервера (`ZALI_DATA_DIR`,
   **не** чекаут исходников) и посчитать SHA-256 (`shasum -a 256 <file>`).
   Отдаётся публично на `https://msgs.zalikus.org/releases/<filename>`.
4. **Подписать релиз:** `python3 scripts/release_sign.py --platform … --version …
   --file … --url …` (приватный ключ разработчиков — вне репозитория). Клиенты
   качают обновление только при действующей подписи над платформой, версией,
   SHA-256 и ссылкой; релиз без `signature` они не ставят. Сервер проверяет
   подпись при публикации (400, если не сходится).
5. `POST /api/version` с телом из шага 4 (нужен `RELEASE_ADMIN_TOKEN` в env
   сервера — иначе роут всегда 403). Выполнять `curl` **на сервере**, чтобы токен
   не покидал его; приватный ключ подписи на сервер не копировать.
6. Проверить и метаданные (в том числе непустой `signature`), и что артефакт реально качается без авторизации:
   `curl "https://msgs.zalikus.org/api/version?platform=macos"` и
   `curl -o /dev/null -w '%{http_code} %{size_download}\n' <downloadUrl>`.

## Ловушки

- **`/uploads/:filename` не годится для артефактов.** Это роут вложений:
  `download_upload_file` требует `AuthenticatedUser` и строку в `messages` с
  таким `filename` — `.exe` оттуда отдаёт 401. Апдейтер и онлайн-установщик
  качают **без** `Authorization`. Для этого есть публичный
  `GET /releases/:filename` (`server/src/updates.rs`): читает только из
  `releases_dir`, имя проходит allowlist `[A-Za-z0-9._-]` без ведущей точки,
  листинга нет. Тесты — `tests/releases.rs`.
- **Публикация той же версии, что уже стоит у клиента, не делает ничего — молча.**
  `checkForAppUpdate()` выходит на `compareVersions(latest, current) <= 0` без
  сообщения и без записи в лог — неотличимо от сломанного апдейтера. Первым
  делом сравнить опубликованную версию с зашитой в клиент.
- **Установочный скрипт исполняет СТАРАЯ версия.** Фикс апдейтера начинает
  действовать только со следующего релиза — у пользователей на сборке с багом
  нужен один ручной установ.
- **macOS: линкер падает на разросшемся веб-бандле.** `Assets.swift` получает
  HTML+CSS+JS Swift-литералами; каждый литерал — один `__cstring`-атом, ld64
  именует атом его содержимым и падает на имени больше ~1 МиБ:
  `ld: Assertion failed: (name.size() <= maxLength), function makeSymbolStringInPlace`
  — без имени файла или символа в ошибке. `bundle_web.py` режет бандл на куски
  по 200 000 символов (`max_chunk_chars`) — если ассерт вернётся, уменьшить это
  значение. Разбиение по границам строк, склейка `joined(separator: "\n")`,
  закрывающий `"""#` в нулевой колонке — это осознанно, для побайтового
  соответствия исходнику.
- **macOS: абсолютный путь к dylib убивал все прежние релизы (найдено
  2026-09-09).** `core` собирается как cdylib+staticlib, линкер по `-l`
  предпочитает `.dylib` — бинарник получает зависимость на
  `<repo>/core/target/release/deps/libzali_messenger_core.dylib` по
  абсолютному пути. На машине сборки незаметно, у скачавшего релиз dyld
  библиотеку не находит, приложение не стартует вообще. `build_app.sh` кладёт
  копию в `Contents/Frameworks`, переписывает на `@rpath` и **после подписи
  проверяет**, что среди зависимостей не осталось путей внутрь репозитория —
  не убирать эту проверку, поломка видна только на чужой машине. Признак
  старой сборки — zip ~1.2 МБ вместо ~1.5 МБ.
- **macOS: апдейтер сначала отодвигает старый бандл, не удаляет.**
  `UpdateService.installAndRelaunch` — раньше был `rm -rf` установленного
  `.app` + непроверенный `mv`; сбой переименования уничтожал установку и не
  запускал ничего. Теперь при любом исходе что-то стартует обратно, причина —
  в `updates/install.log`.
- **Windows: скрипт установки — только `CREATE_NO_WINDOW`.** С
  `DETACHED_PROCESS` этот флаг игнорируется, и у отсоединённого процесса нет
  консоли — каждая консольная утилита в скрипте получала своё окно
  (всплывающий `find "<pid>"`). Ожидания `tasklist`/`find`/`timeout` нет:
  Windows держит запущенный образ заблокированным, повтор `copy` и есть
  ожидание (`timeout` к тому же требует консольного ввода и падал мгновенно).
  После 60 попыток скрипт возвращает уже установленную версию, причина — в
  `updates/install.log`; путь реальный, установщик кладёт в Program Files,
  куда неэлевированная копия запрещена.
- Cross-build (`cargo xwin`) даёт валидный бинарник, но **ничего не говорит о
  поведении** — трей, автозапуск, toast, AUMID, установщик и сам апдейтер
  нужно прогнать на живой Windows перед публикацией.
