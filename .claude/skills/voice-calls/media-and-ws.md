# Голосовые звонки: медиа и WS keepalive

Часть скилла `voice-calls` (основной файл — `.claude/skills/voice-calls/SKILL.md`).

## Медиа

- **Битрейт видео/шаринга делится на состав комнаты** (`voiceVideoBudget` /
  `applyVoiceVideoBitrateLimit`). В mesh каждая камера кодируется на каждого
  пира — без лимита пятеро с камерами просят 4–10 Мбит/с с аплинка. Камера
  запрещена больше чем на `MAX_MESH_VIDEO_PEERS` (15), `MAX_MESH_AUDIO_PEERS`
  (15) — только предупреждение в лог. Аудио `maxBitrate` — 64 кбит/с (было
  512 000, что при Opus'овых ~32 кбит/с не ограничивало ничего).
- **Потолки видео (с 2026-11-20, по просьбе пользователя):** камера 2,5 Мбит/с на
  собеседника (всего 5, пол 0,3), экран 8 (всего 16, пол 0,5). Камера — `balanced`, экран — `maintain-resolution` (`balanced` на просевшем канале ужал его до 339×220); экран
  ещё и сжимается до большей стороны `VOICE_SCREEN_MAX_SIDE` (1920). **Лимиты ставятся
  заново после каждого согласования** (`ensureVoiceSenderLimits` из
  `onsignalingstatechange` → stable): поставленный до применения оффера собеседника
  Chromium теряет — у видеоотправителя телефона `maxBitrate` не было вовсе, камера шла с
  умолчанием WebRTC 2500 кбит/с. Демонстрация Mac «Оригинал» 3420×2214 при ~400 кбит/с и
  `maintain-resolution` давала 16 фризов (картинка стояла 8,5 с из 20). Видео в журнале
  звонка — строка `video-health` (кодек, кодировщик, разрешение, fps, кбит/с, ограничение,
  потери, фризы) рядом с `audio-health`.
- **Замер 2026-11-20 (Mac ↔ Xiaomi, оба на 2,4 ГГц, канал 6, 802.11n 20 МГц):** тогдашние
  потолки (камера 1,2, экран 2,0, звук 0,064 Мбит/с на одного собеседника) не причина
  «сыпется и зависает». Телефон кодирует и камеру, и экран программным VP8 (`encoderImplementation:
  libvpx`, `qualityLimitationReason` по CPU — 0), цель кодировщика ≈ 1,03 / 1,92 Мбит/с;
  повторов 6 % (камера) и 2,7 % (экран), джиттер видео у получателя до 154 мс, оценка
  канала Mac → телефон проседала до 185–611 кбит/с, RTT проверок ICE — до 440 мс. Зависания
  на минуты были не от битрейта, а от заморозки Android-процесса в фоне — лечит
  `OngoingCallService` (скилл `android-client`). Видео-статистики в журнале звонка нет
  (`audio-health` — только звук): снимать `getStats()` через CDP (рецепт в памяти
  `android-live-debug-recipe`).
- **`reportVoiceAudioHealth` должна запускаться на ЗДОРОВОМ звонке.** Ставилась
  под `if (!entry.statsTimer)` на переходе в `connected`, а таймер уже был
  заведён при создании пира — always-on диагностика на здоровых звонках не
  работала никогда. Таймер теперь заводится одним владельцем
  (`ensureVoicePeerStatsTimer`).

## WebSocket keepalive (`server/src/realtime.rs`)

- Сервер шлёт протокольный `Ping` каждые 20 с. Установившийся звонок не
  создаёт WS-трафика (медиа P2P), собственный ping клиента — `setInterval`,
  который браузеры душат в фоновой вкладке; реверс-прокси закрывал такие
  соединения по idle. Ping/Pong обрабатывает сетевой стек браузера без
  пробуждения JS.
- **У КАЖДОГО клиентского сокета должен быть дедлайн ответа на пинг, а не
  только отправка пинга.** На обрыве без FIN отправка «успешна» минутами. До
  2026-09-10 дедлайн был только у голосовых сокетов: главный сокет сообщений
  macOS (`scheduleHeartbeat`, 20 с) и Windows (`run_message_transport`, 70 с
  без входящих кадров) висели полуоткрытыми с зелёным значком. Android закрыт
  OkHttp `pingInterval`, браузер/iOS — JS-сторожем в
  `connectBrowserVoiceSocket`. С 2026-11-18 у Windows 20 с (`WS_PONG_DEADLINE`).
- **Смена сети и пробуждение — сразу проба, а не ожидание тика** (2026-11-18). macOS
  (`kickConnections`: `NWPathMonitor` + `NSWorkspace.didWakeNotification`), Android
  (`kickConnections`: `registerDefaultNetworkCallback`), браузер
  (`kickBrowserVoiceSocket`: `online` и возврат вкладки), Windows (`PongWatchdog`:
  скачок настенных часов между тиками = сон). Ждущий бэкоффа реконнект стартует
  немедленно; открытый сокет получает ping с дедлайном 5 с — жив, значит остаётся
  (без ложного false→true и лишней догрузки истории). Дедлайн ответа на обычный
  пинг у Windows теперь 20 с, как у macOS (был 70 с). HTTP-пулы на событие
  сбрасываются (`URLSession.flush`, `connectionPool.evictAll`).
- **TCP_NODELAY везде, где ходят мелкие кадры**: сервер (`axum::serve(...).tcp_nodelay`)
  и WS Windows (`connect_ws` → `connect_async_with_config(.., true)`). С Нейглом
  пачка ICE-кандидатов ждала delayed ACK — до 200 мс на Windows.
- **HTTP-пул держится тёплым, пока есть сессия** (`scheduleApiWarmup` на
  macOS, `warm_api_connections` в `native.rs`, `warmApiConnection` в
  `NativeBridge.kt` — на Android только пока приложение на экране). Раз в
  минуту — крошечный публичный `GET /api/version` без `Authorization`. Пул
  остывает между сообщениями, первая отправка после паузы платит полный
  TCP+TLS — 390 мс против 155 мс по живому соединению.
- **Не возвращать отключение по тишине.** 70-секундный idle-timeout, введённый
  вместе с Ping, убил 27 живых соединений за первые сутки — судит о живости
  по отсутствию входящих кадров, а не все клиенты отвечают на Ping (у
  `tokio-tungstenite` при разделённом стриме Pong ставится в очередь и не
  отправляется, пока не опрашивают write-половину). Мёртвые соединения
  детектируются по ошибке отправки. Если проблема с фоновыми вкладками
  вернётся — слать Ping без привязанного таймаута.

## Выбор камеры и источника демонстрации (`voice_devices.js`)

- **Только веб-слой.** macOS (WKWebView) и Windows (WebView2) отдают
  `getUserMedia`/`getDisplayMedia` самим движком, Android показывает системный диалог
  MediaProjection — пикер там не показывается (`toggleScreenShare`).
- **Список конкретных экранов/окон веб-слою недоступен.** Пикер выбирает
  КАТЕГОРИЮ (`displaySurface`, `monitorTypeSurfaces` — подсказки, неизвестные
  движку ключи игнорируются; `TypeError` → повтор без них) и качество; сам источник
  выбирает системное окно. Настоящий список с миниатюрами потребует нативного
  перечисления (ScreenCaptureKit / Windows.Graphics.Capture) в обоих шеллах.
- **Камера:** выбор хранится в `zali_voice_camera_v1` как `ideal` deviceId — отключённая
  камера молча заменяется системной, а не рвёт включение. Смена на лету
  (`switchVoiceCamera`) берёт новый трек ДО остановки старого и делает `replaceTrack`.
- **Звук демонстрации экрана** (`startScreenShare`, пикер «Звук», по умолчанию вкл):
  `getDisplayMedia({audio})` + `systemAudio: 'include'`; аудиодорожка едет в ТОМ ЖЕ
  MediaStream, что и картинка (`entry.screenAudioSender`). Отдаёт только Chromium
  (Windows/WebView2; macOS WKWebView — нет), иначе демонстрация идёт без звука
  (`voice.screenAudioShared=false`, запись в логе). **Инвариант приёма:**
  аудиодорожка потока с id, отличным от уже играющего голоса человека, — звук
  экрана (`isRemoteScreenStream`), а не его микрофон; иначе она вытесняла голос в
  `remoteAudios`. Играет из `<video>` плитки: до «Смотреть» — без звука,
  громкость 0–100 % в `audioPrefs.screenVolumePercents`, ПКМ по плитке
  (`openScreenContextMenu`), «Звук» (deafen) глушит и его. Android (canvas-захват)
  звука не имеет.
- **Микрофон и другие приложения (macOS).** WebKit включает эхо-/шумоподавление через
  системный VoiceProcessingIO; пока он держит вход, другие приложения слышат с микрофона
  тишину. Поэтому `micAudioConstraints()` (prefs.js) на WebKit/macOS по умолчанию шлёт
  `echoCancellation/noiseSuppression/autoGainControl: false`; в Chromium (Windows,
  Android) — `true`. Выбор — `audioPrefs.voiceProcessing` (чекбокс в настройках),
  применяется на лету через `setAudioInputDevice`. Любой новый `getUserMedia({audio})`
  обязан брать ограничения оттуда, а не `audio: true`.
- **Мигание видео.** Не присваивать `srcObject` на каждое событие дорожки и не сносить
  `<video>` на краткий `mute`: `attachRemoteVideoStream` ждёт 2,5 с (`_dropTimer`),
  `ended` убирает сразу; плитка получает `has-video` только после первого кадра
  (`readyState >= 2`).
- **Кольцо «говорит»** сглажено (`applyVoiceSpeakingState`: рост 0,5 / спад 0,16 за такт
  80 мс, удержание 350 мс); не возвращать сырой уровень анализатора в CSS-переменную.
