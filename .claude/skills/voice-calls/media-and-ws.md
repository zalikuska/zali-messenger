# Голосовые звонки: медиа и WS keepalive

Часть скилла `voice-calls` (основной файл — `.claude/skills/voice-calls/SKILL.md`).

## Медиа

- **Битрейт видео/шаринга делится на состав комнаты** (`voiceVideoBudget` /
  `applyVoiceVideoBitrateLimit`). В mesh каждая камера кодируется на каждого
  пира — без лимита пятеро с камерами просят 4–10 Мбит/с с аплинка. Камера
  запрещена больше чем на `MAX_MESH_VIDEO_PEERS` (15), `MAX_MESH_AUDIO_PEERS`
  (15) — только предупреждение в лог. Аудио `maxBitrate` — 64 кбит/с (было
  512 000, что при Opus'овых ~32 кбит/с не ограничивало ничего).
- **`reportVoiceAudioHealth` должна запускаться на ЗДОРОВОМ звонке.** Ставилась
  под `if (!entry.statsTimer)` на переходе в `connected`, а таймер уже был
  заведён при создании пира — always-on диагностика на здоровых звонках не
  работала никогда. Таймер теперь заводится одним владельцем
  (`ensureVoicePeerStatsTimer`).

## WebSocket keepalive (`server/src/realtime.rs`)

- Сервер шлёт протокольный `Ping` каждые 20 с. Установившийся звонок не
  создаёт WS-трафика (медиа P2P), собственный ping клиента — `setInterval`,
  который браузеры душат в фоновой вкладке; реверс-прокси закрывал такие
  соединения по idle. Ping/Pong обрабатывает сетевой стек браузера без
  пробуждения JS.
- **У КАЖДОГО клиентского сокета должен быть дедлайн ответа на пинг, а не
  только отправка пинга.** На обрыве без FIN отправка «успешна» минутами. До
  2026-09-10 дедлайн был только у голосовых сокетов: главный сокет сообщений
  macOS (`scheduleHeartbeat`, 20 с) и Windows (`run_message_transport`, 70 с
  без входящих кадров) висели полуоткрытыми с зелёным значком. Android закрыт
  OkHttp `pingInterval`, браузер/iOS — JS-сторожем в
  `connectBrowserVoiceSocket`.
- **HTTP-пул держится тёплым, пока есть сессия** (`scheduleApiWarmup` на
  macOS, `warm_api_connections` в `native.rs`, `warmApiConnection` в
  `NativeBridge.kt` — на Android только пока приложение на экране). Раз в
  минуту — крошечный публичный `GET /api/version` без `Authorization`. Пул
  остывает между сообщениями, первая отправка после паузы платит полный
  TCP+TLS — 390 мс против 155 мс по живому соединению.
- **Не возвращать отключение по тишине.** 70-секундный idle-timeout, введённый
  вместе с Ping, убил 27 живых соединений за первые сутки — судит о живости
  по отсутствию входящих кадров, а не все клиенты отвечают на Ping (у
  `tokio-tungstenite` при разделённом стриме Pong ставится в очередь и не
  отправляется, пока не опрашивают write-половину). Мёртвые соединения
  детектируются по ошибке отправки. Если проблема с фоновыми вкладками
  вернётся — слать Ping без привязанного таймаута.

## Выбор камеры и источника демонстрации (`voice_devices.js`)

- **Только веб-слой.** macOS (WKWebView) и Windows (WebView2) отдают
  `getUserMedia`/`getDisplayMedia` самим движком, Android показывает системный диалог
  MediaProjection — пикер там не показывается (`toggleScreenShare`).
- **Список конкретных экранов/окон веб-слою недоступен.** Пикер выбирает
  КАТЕГОРИЮ (`displaySurface`, `monitorTypeSurfaces` — подсказки, неизвестные
  движку ключи игнорируются; `TypeError` → повтор без них) и качество; сам источник
  выбирает системное окно. Настоящий список с миниатюрами потребует нативного
  перечисления (ScreenCaptureKit / Windows.Graphics.Capture) в обоих шеллах.
- **Камера:** выбор хранится в `zali_voice_camera_v1` как `ideal` deviceId — отключённая
  камера молча заменяется системной, а не рвёт включение. Смена на лету
  (`switchVoiceCamera`) берёт новый трек ДО остановки старого и делает `replaceTrack`.
