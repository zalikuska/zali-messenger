# Голосовые звонки: нативный захват (macOS, Windows)

Часть скилла `voice-calls` (основной файл — `.claude/skills/voice-calls/SKILL.md`).
Веб-сторона — `web/src/interface/native_media.js`, обработка звука —
`core/src/audio_processing.rs` (фича `apm`), её тесты — `core/tests/apm_quality.rs`.

## Зачем

WebKit (WKWebView) на macOS захватывает микрофон только через системный
VoiceProcessingIO — даже с `echoCancellation: {exact:false}`. На каждый вход в звонок
это `AudioDeviceDuck(…, 0.177828)` (все остальные приложения тише на 15 дБ), агрегат
«микрофон + динамики» и `StopForReconfiguration` — звук во всей системе заикается
(журнал 2026-11-12, `/usr/bin/log show --predicate 'eventMessage CONTAINS "AudioDeviceDuck"'`).
Поэтому на десктопе устройства открывает оболочка, а WebRTC остаётся в WebView.

**Инвариант:** на macOS и Windows `getUserMedia`/`getDisplayMedia` — только запасной путь
(нативный отказал или возможность не объявлена). Новый захват в веб-коде идёт через
`tryNativeMicStream` / `captureVoiceCameraTrack` / `openNativeMediaStream`, не мимо них.
Android и браузер — по-прежнему движок (там AEC/NS движка безвредны). Исключение —
**экран на Android** (с 2026-11-22): у Android WebView нет `getDisplayMedia`, поэтому
оболочка объявляет `nativeScreen` и транспорт `webmessage` (ниже) и кодирует экран
аппаратно: VirtualDisplay → входная поверхность MediaCodec → H.264 Annex B
(`ScreenH264Encoder.kt`, `ScreenCaptureService.startH264Capture`). Источник один — весь
экран, согласие — системное окно MediaProjection (поэтому `start` ждёт до 120 с,
`startTimeoutMs`); звука экрана нет. Без WebMessage с ArrayBuffer (старый WebView) —
прежний путь JPEG → data: URL → `canvas.captureStream(8)` (`startNativeScreenCapture`,
~8 к/с). На телефоне не проверено — только эмуляцией оболочки в Chrome
(`scripts/voice_doctor/sfu_e2e/android_sim.mjs`: 1080×2400@30 до зрителя через SFU).

## Возможности

Оболочка объявляет в `__ZALI_NATIVE_CAPS__` только то, что реализовала:
`nativeMic`, `nativeCamera`, `nativeScreen`, `nativeScreenAudio`, `nativeSfuScreen` (ниже). Без флага веб идёт в
движок — можно выкатывать по частям. Плюс `window.__ZALI_MEDIA_BRIDGE` (user-скрипт
основного фрейма, `atDocumentStart`):

- macOS: `{kind: 'websocket', url: 'ws://127.0.0.1:<порт>/media', token: '<одноразовый>'}`.
  Сервер — только `127.0.0.1`, случайный порт; первым сообщением страница шлёт текст
  `{"hello":"<token>"}`; оболочка закрывает соединение при неверном токене или
  `Origin` ≠ `http://localhost`; второе одновременное соединение не принимается (новое
  вытесняет старое только после проверки токена). Токен не попадает в URL и журнал.
- Windows: `{kind: 'sharedbuffer'}`; кадры — `ICoreWebView2_17::PostSharedBufferToScript`
  только верхнему фрейму `zali.localhost`, буфер из `ICoreWebView2Environment12::CreateSharedBuffer`,
  доступ `READ_ONLY`. Страница сразу вызывает `chrome.webview.releaseBuffer` (данные
  копирует). **Буфер — новый на каждый кадр**, сразу `Close` после отправки: страница не
  сообщает оболочке, что скопировала кадр, и запись в тот же буфер по кругу давала бы
  рваные кадры. Пул — только вместе с подтверждением от страницы.
- Android: `{kind: 'webmessage'}` (только верхнему фрейму, вместе с `__ZALI_BRIDGE_NONCE__`).
  Страница шлёт `MEDIA_REQUEST` `op: 'transport'`; оболочка создаёт WebMessage-канал и
  отдаёт один конец сообщением `"zali-media-port:<nonce>"` — страница принимает порт ТОЛЬКО
  с этим текстом (песочница аддонов может слать окну сообщения, но секрета не знает). По
  порту — ArrayBuffer с кадрами; порт живёт на главном потоке, больше 6 кадров в очереди —
  разностные выбрасываются и кодировщик даёт ключевой. SPS/PPS — внутри каждого ключевого
  кадра (декодер страницы настроен без `description`).
- Windows: Media Foundation (`mf`, `mfplat`, `mfreadwrite`) грузится динамически, а не
  через таблицу импорта: на Windows N без Media Feature Pack иначе не запускалось бы всё
  приложение — там просто нет камеры. Перезагрузка страницы останавливает все нативные
  потоки, чтобы микрофон и камера не оставались занятыми до выхода.

## Управление: `MEDIA_REQUEST` → событие шины `media_event`

`{type:'MEDIA_REQUEST', op, requestId?, stream?, kind?, deviceId?, sourceId?, options?}`.
Ответ на запрос с `requestId` — `media_event` с тем же `requestId`; ошибка —
`{event:'error', requestId, code, message}`, `code`: `permission` (нет доступа TCC/
приватности), `not_found`, `busy`, `unsupported`, `failed`.

| op | поля | ответ |
|---|---|---|
| `list_devices` | — | `{event:'devices', audioinput:[{id,label,isDefault}], videoinput:[…]}` |
| `list_screen_sources` | `options.thumbWidth` | `{event:'screen_sources', sources:[{id, kind:'display'\|'window', title, app, own, width, height, thumb}]}` — `thumb` = `data:image/jpeg;base64,…` шириной ≤ thumbWidth; окна самого мессенджера в списке с `own: true` (их можно показать); id стабилен, пока источник жив |
| `start` | `stream` (число, выдаёт страница), `kind` `mic`/`camera`/`screen`, `deviceId`/`sourceId` (пусто = по умолчанию), `options` | `{event:'started', stream, codec, label, deviceId}` — `codec` для H.264 — строка `avc1.PPCCLL` |
| `stop` | `stream` | — (ответа нет) |
| `set_processing` | `options: {aec, ns, agc}` | — ; применяется к идущему микрофону на лету |
| `request_keyframe` | `stream` | — ; ближайший кадр — ключевой |
| `rc_grant` | `stream` (поток экрана), `options.peer` | нативный диалог согласия → `{event:'rc_granted', stream}` или ошибка `denied`/`permission`/`busy`/`not_found` (без `stream` в ошибке) |
| `rc_input` | `stream`, `options` = событие ввода | — ; без журнала, до 60/с; игнорируется без разрешения |
| `rc_revoke` | `stream` | — |
| `start` c `kind:'browser'` | `stream`, `options: {url, profile:'own'\|'community', cookies, width, height, fps}` (`fps: 0` — частота экрана запустившего) | как у экрана + `fps` (выбранная частота); кадры — со скрытого браузера оболочки |
| `browser_input` | `stream`, `options` = событие ввода | — ; без журнала, до 60/с |
| `browser_nav` | `stream`, `options: {action:'go'\|'back'\|'forward'\|'reload'\|'stop', url}` | — |
| `browser_cookies` | `stream` | `{event:'browser_cookies', stream, cookies}` (формат CDP `Network.Cookie`) |

**Удалённое управление** — управление **не просят, его отдаёт сам показывающий**: кнопка «Отдать
управление» на плитке «Ваш экран» → выбор участника (в личном звонке — сразу он) → нативное
подтверждение → право действует, пока идёт **эта** демонстрация всего экрана (конец демонстрации,
выход из звонка, «Забрать управление»/«Остановить», «Вернуть управление» у зрителя — снимают).
Одному участнику за раз: выдача другому сначала забирает у прежнего. Компонент **выключен по
умолчанию**: «Настройки → Компоненты» (`zali_component_remote_control_v1`, только локально — в облако
настроек не уходит); выключен у показывающего — кнопки нет, у получателя — право сразу возвращается
(`rc-release`, `reason: 'disabled'`); выключение обрывает сеанс. (`rc_*`, флаг `nativeRemoteControl`;
веб — `web/src/interface/remote_control.js`, оболочки — `Services/Media/RemoteControl.swift`,
`native/media/remote_control.rs`, проверка — `scripts/voice_doctor/check_remote_control.mjs`.)
Подтверждает **оболочка своим диалогом** даже после клика на странице (NSAlert / MessageBoxW, 100 с —
поздний ответ = отмена): JS не может отдать управление сам, случайный клик — тоже. Диалог крадёт фокус
посреди набора текста, поэтому: macOS — «Отдать управление» неактивна первые 1,5 с; Windows — **ОК/Отмена,
не Да/Нет** (у «&Да»/«&Yes» мнемоника: буква «д»/«y» отдала бы управление), «Отмена» по умолчанию, ответ
быстрее 1,5 с — окно заново. Имя в диалоге оболочка сама сводит к алфавиту логинов (`[A-Za-z0-9_-]{1,32}`):
сервер может быть чужим. Разрешение — только для живого потока `display:` (окно не годится — его
координаты плывут), снимается с концом этого потока (`{event:'rc_revoked', stream, reason}`), при
`stop_all`/закрытии моста (перезагрузка страницы) и по `rc_revoke`; при снятии оболочка отпускает всё,
что держала нажатым. События ввода: `{t:'move',x,y}`, `{t:'down'|'up',x,y,b:0|1|2}`, `{t:'wheel',dx,dy}`
(пиксели, знак как у веба), `{t:'key',code,d}` (`KeyboardEvent.code`, физическая клавиша),
`{t:'release'}`; x/y — доли кадра. macOS вводит через CGEvent и требует «Универсальный доступ» (без
него — `permission` и системный запрос); Windows — SendInput (окна администратора и Ctrl+Alt+Del
недоступны). Между клиентами: сигналы `rc-grant`/`rc-revoke` (показывающий → зритель) и
`rc-release`/`rc-input` (зритель → показывающий) в `voice_signal` (сервер их не разбирает); ввод —
RTCDataChannel `zali-rc`, который создаёт зритель, получив право (первый канал на соединении →
пересогласование); до его открытия — `rc-input` через сервер, **только мышь** (движения ≤ 10/с):
клавиши через сервер видел бы его оператор, показывающий их оттуда не принимает.

**«Общий браузер»** — активность звонка: запустивший открывает **скрытый встроенный браузер оболочки**
(не Safari/Chrome и не профиль мессенджера), его кадры идут обычной демонстрацией (`startScreenShare({browser})`,
`voice.screenActivity = 'browser'`), управляют все участники, у каждого курсор цвета своей аватарки
(самый насыщенный тон картинки, иначе — из имени). Профиль: «мой» — выделенный профиль приложения на
компьютере запустившего; «сообщества» — куки с сервера (`GET/PUT /api/servers/:id/browser-profile`,
`server/src/browser_profiles.rs`, только участники, **не E2E** — у сообщества нет секрета вне сервера),
сохраняются после загрузки страниц, раз в минуту и при «Закрыть браузер» (сохранения идут по одному: закрытие
ждёт идущего автосохранения). PUT несёт `baseRevision`: совпала — набор заменяет хранимый, нет — сервер
сливает по (домен, путь, имя), чтобы два одновременных браузера не затирали входы друг друга; лишнее
обрезается (просроченные, затем ≤ 600 штук и 384 КиБ), а не отклоняется. Флаг `nativeSharedBrowser`
(macOS, Windows); остальные клиенты — только зрители и управляющие. Веб — `web/src/interface/shared_browser.js`,
оболочки — `Services/Media/SharedBrowser.swift`, `native/media/shared_browser.rs`, проверка —
`scripts/voice_doctor/check_shared_browser.mjs`, тест сервера — `tests/browser_profiles.rs`.
Между клиентами — звезда через запустившего: участник создаёт канал `zali-sb` (сразу, получив `sb-state`),
шлёт события ввода в долях кадра (`move/down/up/wheel/key{code,key,m}/text/nav/leave`), запустивший
раздаёт `{t:'cursors'}` ~20 Гц; сигналы `sb-state`/`sb-end` (запустивший → все) и `sb-input` (без канала —
**только мышь и навигация**). Фильтр и в странице, и в оболочке: Cmd/Ctrl — только редактирование и
навигация по тексту (**никакой вставки/копирования/вырезания**: вставка отдала бы буфер запустившего,
копирование подменило бы его); свой текст участник вставляет из **своего** буфера (`{t:'text'}`).
«Управляю только я» у запустившего отбрасывает чужой ввод (курсоры видны). Оболочка: только http(s);
loopback/локальная сеть закрыты и для навигации, и для подзапросов (Windows — фильтр по шаблонам
`PRIVATE_URL_PATTERNS`, не на всё: обработчик в потоке окна мессенджера); загрузки, выбор файла, разрешения,
новые окна (открываются в том же), диалоги скриптов — запрещены; куки и адреса в журнал не пишутся.
Осталось: DNS-rebinding (имя → 127.0.0.1) правилами по адресу не ловится; звука у браузера нет.
macOS: окно без рамки за экраном, `_setWindowOcclusionDetectionEnabled:` выключен (иначе страница
«засыпает»), `isKeyWindow` подменён и наведение — через `_simulateMouseMove:` (обычный `mouseMoved`
WebKit в неактивном окне не пропускает), кадры — `takeSnapshot` → BGRA → H.264 (разрешение на запись
экрана не нужно), колесо — CGEvent с «экранной» точкой = точке в окне; профиль «мой» — macOS 14+
`WKWebsiteDataStore(forIdentifier:)`, на 13 — временный + куки в файле. Windows: WS_POPUP за экраном
(WS_EX_TOOLWINDOW|NOACTIVATE), отдельный WebView2 со своим каталогом (`SharedBrowser/own`,
`SharedBrowser/session-*` — удаляется) и `--disable-features=…CalculateNativeWinOcclusion`, кадры —
`screen::run` по `window:<hwnd>`, ввод и куки — протокол DevTools, масштаб растеризации 1.0.
**На живом Windows не проверялось** (только `cargo xwin check` и юнит-тесты правил).
Частота кадров — **частота экрана запустившего** (macOS — `NSScreen.main.maximumFramesPerSecond`, Windows —
частота основного монитора; 30…240, страница шлёт `fps: 0`, оболочка отвечает фактической в `started.fps`).
Отправка в звонок для браузера: `maxFramerate` = эта частота (иначе потолок WebRTC — 60), `degradationPreference:
'maintain-framerate'` (при нехватке канала падает разрешение, не плавность), бюджет 20 Мбит/с на всех
(1…10 на собеседника; с 2026-11-20, вместе с экраном 8), дорожка `contentHint: 'motion'`. Стенд macOS (M5, 2026-11-16): 60 к/с — 0 опоздавших
кадров из 600, снимок 3–4 мс, ~28% ядра на статичной странице и ~48% на анимации во весь кадр; 120 к/с — 1 из
1200, ~47%. Одинаковые кадры не кодируются (точное сравнение с прошлым; повтор раз в секунду), полсекунды
без изменений — снимается каждый 4-й тик, ввод сразу возвращает полную частоту: статичная страница ~12% ядра.
Ровность — в `stats.video` (`late`, `max_gap_ms`, `busy_ticks`, `snapshot_ms`, `idle_ticks_skipped`,
`repeats_skipped`). Скрытое окно не попадает в «Что показать» (`SharedBrowser.isHiddenWindow`).

Опции `start`: микрофон `{processing: bool}`; камера `{width, height, fps}`; экран
`{fps, maxHeight (0 = оригинал), audio, cursor}`; браузер `{url, profile, cookies, width, height, fps}`.

События без запроса: `{event:'ended', stream, reason}` (источник пропал, окно закрыли,
устройство отключили) — страница гасит дорожку и шлёт `ended` (→ `stopScreenShare`);
`{event:'devices_changed'}`; `{event:'transport_unavailable'}` (Windows: нет общей памяти
WebView2 — страница выключает нативный захват до перезагрузки, без ожидания таймаутов); `{event:'stats', stream, processing:{erle_db, delay_ms, …}}`
раз в 10 с для микрофона (уходит в `voiceDiag mic-processing-native`).

Камера, открытая двумя потоками (превью в окне выбора + звонок), — один сеанс захвата
с раздачей кадров обоим, а не два сеанса (AVFoundation/MF отдают устройство одному).
Режим сеанса — **наибольший из запрошенных**: превью просит 640×360, звонок 1280×720;
если звонок подписался вторым, режим растёт на ходу (macOS — `CameraHub.prepare`,
Windows — `Shared.want` + `configure_reader` на том же читателе), иначе звонок остался
бы в размере превью и после его закрытия.

**Неподвижный экран:** ScreenCaptureKit и WGC отдают кадр только при изменении картинки,
а у каждого собеседника свой кодировщик WebRTC. Оболочка повторяет последний кадр не
реже раза в секунду — иначе вошедший в звонок видит чёрный экран, пока на нём ничего не
сдвинется.

`stats.processing.reference` — `bool` (есть ли опорный сигнал) на обеих платформах;
macOS дописывает причину в `reference_status` (`tap`, `off`, `unsupported-os`, `failed: …`).

**Старые id устройств.** Выбор камеры/микрофона, сохранённый до нативного захвата, — id
движка (WebKit/Chromium хешируют его по origin); оболочка его не знает (`not_found`).
Страница тогда открывает устройство по умолчанию **из оболочки**, а не уходит в
getUserMedia (на macOS это снова VoiceProcessingIO): `tryNativeMicStream`,
`captureVoiceCameraTrack`, превью в окне выбора — одним флагом `defaultIfUnknown` в
`openNativeMediaStream`. В журнале — `native-media-unknown-device`.

**Звук самого приложения в демонстрации** (`web/src/interface/share_audio.js`). Оболочка
снимает звук системы без всего ZaliMessenger — иначе голоса собеседников вернулись бы
им. Остальной звук приложения собирает страница в контексте звуков (`this.sound.ctx`) и
подмешивает к звуку оболочки (`startShareAppAudio`), при показе **всего экрана** и
**окна мессенджера** (окно другого приложения — только его звук):

| Источник | В демонстрации |
|---|---|
| голоса звонка, звук чужих демонстраций | нет (свои `<audio>`/`<video>`, сюда не заводятся) |
| звуки звонка (вход/выход, начало показа) — `playSoundBuffer('voice')` | нет: зрители в том же звонке |
| уведомления, рингтоны (`soundBus`, `soundDirectSharedBus`) | приглушённо, `SHARE_DUCK_GAIN` = 0.25 (вчетверо, ≈ −12 дБ) |
| видео/аудио вложений (`.media-video`, `.media-audio-player`, blob:/data:) | как есть; `createMediaElementSource` при первом `play` во время показа — дальше элемент всегда звучит через контекст |
| аддоны (sandbox iframe), чужой origin без CORS | нет — недостижимы / дали бы тишину и в динамиках |

Новый звук приложения — через `soundDirectSharedBus` (попадёт в стрим) или
`soundDirectBus` (только в динамики); никогда не мимо обоих прямо в `ctx.destination`.

### Журнал

| Где | Что |
|---|---|
| macOS `zali-debug.log`, `[ZALI][MEDIA]` | каждый запрос (`request op=… device=<12 символов>`), `screen sources: N (thumbs M) in X ms`, раз в 10 с `stats stream=…` видео (кадры, fps, кбит/с, ключевые, пропуски, повторы неподвижного экрана, кадры камеры, формат), затор транспорта, пересборка формата камеры, сбои кодировщика, число запросов ключевого кадра |
| Windows `zali-win.log`, `[ZALI][WIN] media` | запрос, `started`/`ended`/`failed` с причиной, раз в 10 с `stats` видео (кадры, пропуски, кадры камеры, повторы, GPU/CPU-перевод), смена режима камеры |
| Журнал звонка (страница) | `native-media-open` → `native-media-started ms=…` / `native-media-open-failed`, `native-video-stats` (цифры оболочки + сколько кадров дошло до страницы; WARN при пропусках или нуле кадров), `mic-processing-native`, ошибки и отставание декодера, `native-media-ended` с длительностью и числом кадров, `voice-panel-rebuild` (панель пересобрана при живом видео — кадр мигнёт) |

`mic-processing-native` кроме AEC несёт уровни за ~5 с: `input_dbfs`, `output_dbfs`,
`noise_in_dbfs`/`noise_out_dbfs` (кадры без голоса до и после RNNoise),
`ns_attenuation_db` (сколько срезал шумодав; белый шум в тесте — ~20 дБ),
`noise_final_dbfs` (те же шумовые кадры после AGC — если заметно выше `noise_out_dbfs`,
AGC поднимает шум в паузах), `gate_closed_ratio` / `gate_depth_db` (затвор шумодава, ниже),
`speech_ratio`, `clipped_frames`; склейка с опорным сигналом
(ниже): `ref_lag_ms` (насколько опорный приходит позже микрофона), `hold_ms` (сколько
микрофон его ждёт), `ref_zero_frames`, `ref_forced_frames`, `ref_late_dropped`. Рабочий
AEC — `erle_db` десятки дБ и `delay_ms` > 0; `erle_db` 0–9 при живом опорном — сбой склейки.

## Кадры

32 байта заголовка (little-endian) + данные, по кадру на сообщение/буфер:

| смещение | тип | поле |
|---|---|---|
| 0 | u8 | `0x5A` |
| 1 | u8 | версия = 1 |
| 2 | u8 | вид: 1 звук, 2 видео |
| 3 | u8 | кодек: звук 1 = f32 PCM 48 кГц; видео 1 = H.264 Annex B, 2 = NV12, 3 = H.265 Annex B, 4 = AV1 (OBU) — 3/4 только превью нативной демонстрации через SFU |
| 4 | u32 | `stream` |
| 8 | u64 | метка времени, мкс (монотонная) |
| 16 | u16 | ширина (чётная) |
| 18 | u16 | высота (чётная) |
| 20 | u8 | флаги: бит 0 — ключевой кадр |
| 21 | u8 | каналы (звук) |
| 22 | u16 | резерв |
| 24 | u32 | длина данных |
| 28 | u32 | номер кадра |

- **Звук микрофона:** моно, уже после APM, блоки по 10–20 мс. **Звук экрана:** стерео
  (каналы = 2) чередующимися f32, без обработки, тем же `stream`, что и видео экрана.
- **Видео macOS:** H.264 Annex B (VideoToolbox: realtime, без B-кадров, профиль High или
  Main, SPS/PPS перед каждым ключевым кадром, ключевой раз в 2 с и по `request_keyframe`).
  WebKit декодирует `VideoDecoder` → `VideoTrackGenerator` в воркере. **Windows:** NV12
  без сжатия (Chromium `VideoFrame` из буфера, без копии на стороне оболочки).

## Экран напрямую на SFU — macOS, Windows, Android (с 2026-11-22: `core/src/sfu_publisher.rs`)

Раньше в звонке через SFU экран кодировался дважды: VideoToolbox → страница декодирует →
WebRTC WebView снова кодирует simulcast. Теперь оболочка, объявившая `nativeSfuScreen`,
шлёт слои на сервер сама — клиентом WebRTC (str0m, `rust-crypto`) в ядре, фича `sfu`.
**На Windows поток публикатора держит `timeBeginPeriod(1)` и снимает с процесса урезание
таймера Windows 11 (`HighResTimer` в `sfu_publisher.rs`) — не убирать.** Без этого тайм-аут
сокета в цикле идёт шагом ~15,6 мс, пейсер выпускает пачками, оценка канала застревает
около 5 Мбит/с, верхний слой не включается, а Media Foundation на урезанном бюджете
выкидывает кадры (живой Windows → Mac 2026-11-22: 960×540 при 14 к/с). На стенде это
воспроизводится огрублением ожидания до 16 мс в цикле `run()` (`native_pub.mjs`).
**Слои публикатор включает по минимумам (`allocate_layers`, тесты `allocate_tests`), не по
потолкам:** правило «остаток ≥ 60 % потолка» с потолками страницы (h 12, f 40 Мбит/с) держало
h только выше ~5–8 Мбит/с, а f не включало никогда (живой Windows → Mac 2026-11-22).
Оболочка передаёт `min_bitrate` (Windows — `minBps` страницы); без него — 1/10 потолка.
**Потолок слоя у издателя (`max_bitrate`) Windows считает от расчётного битрейта слоя**
(пиксели × к/с × `bpp` страницы × `LAYER_TARGET_HEADROOM` 1,5, в рамках `minBps..maxBps`), а
не берёт `maxBps` страницы: с ним при высокой оценке Wi-Fi кодировщики получали почти весь
канал (h 540p — 5,7 Мбит/с, ключевые 1080p на цели 40 Мбит/с), BWE зондировал до 52 Мбит/с,
и Windows забивала свой же канал: 5–6 % потерь на всём, голос тоже, без демонстрации 0,2 %
(живой Windows → Mac 2026-11-22). Желаемый битрейт BWE — сумма этих потолков.
Стенд с настоящими потолками — `REAL_CAPS=1 node native_pub.mjs`.
**Минимум BWE издателя — ноль: `rtc.bwe().set_bitrate(Bitrate::ZERO, desired)`.** Первый
аргумент str0m — не ориентир, а скорость, которую он держит ПАДДИНГОМ, когда кадров меньше.
Туда шла раздача слоям (0,9 оценки) — потолок кодировщика, а не его выход: статичный экран
кодируется в ~1 Мбит/с, и str0m добивал разницу мусором — до 50 Мбит/с паддинга ради 1 Мбит/с
видео (лог Windows 2026-11-22: оценка 53 Мбит/с, раздача 0,2+7,5+40, отправлено 0,95). Эфир
получателя был забит почти до оценки, каждая пауза Wi-Fi (Mac: ~70 мс раз в 0,5 с) переполняла
очередь точки доступа — голос терял 5–8 %, оценка пилила 2 ↔ 65 Мбит/с, слои выключались и
включались. Канал разведывают пробы str0m, найденная оценка в покое не падает. Признак
возврата: `wire_kbps` в `stats` издателя (и `wire=` в отчёте сервера `[SFU] publisher=`) сильно
больше суммы `sent_kbps`. Стенд с паузами эфира — `zali-server-sfu-rig-wifi`
(`SFU_TEST_STALL=70/520/256`): со старым минимумом ~300 выброшенных пакетов/с и пила оценки,
с нулевым — wire ≈ видео, 1080p60 без фризов.
Включённый слой выключается, только если бюджета не хватает `LAYER_OFF_HOLD` (3 с) подряд,
до этого он держится на минимуме: оценка по Wi-Fi скачет 65 → 2 → 50 Мбит/с за секунды, а
каждое выключение — ключевой кадр и фриз у зрителя.
**Windows: слои SFU выгружаются с GPU конвейером (`Nv12Converter::convert_pipelined`)** —
кадр N на GPU с `Flush`, в кодировщик уходит N−1; когда экран замер, отложенный кадр
дозабирается (`flush_pending`). Синхронный `Map` за каждым `VideoProcessorBlt` на трёх слоях
держал захват на 15 к/с (`captured` ≈150 за 10 с); время подготовки кадра — `convert_ms`
в `media stats`.
Частота слоёв ограничена обновлением дисплея (`display_refresh_hz`) и бюджетом
(`budget_fps`: ≥0,035 бита на пиксель кадра, `eff_fps` в статистике): Media Foundation делит
битрейт на заявленную частоту, и слой «120 к/с» на бюджете 2,5 Мбит/с выкидывал кадры
(1080p на 1–4 к/с, части экрана замирали).
**Ни один закодированный кадр не пропадает молча:** выброшенный из полной очереди ядра
(`push_frame`) или не записанный кадр переводит слой в ожидание ключевого и просит его
(`mark_broken`); иначе P-кадры ссылаются на потерянный — у зрителя застревают куски экрана
и «призраки» курсора до планового ключевого (раз в 10 с). Кадр WGC держится до следующего
(`_held_frame`, пул 3 буфера): без ожидания GPU возвращённую поверхность Windows переписывала
до копирования. Буфер выгрузки чистится перед `pack_nv12` — тот дописывает.
Микрофон Windows пишет `raw_peak_dbfs` в статистику и `mic_digital_silence` (страница
показывает тост), если устройство отдаёт ровные нули: это выключенный доступ классических
приложений к микрофону, WASAPI при этом открывается без ошибки.
- **macOS** — слои VideoToolbox (`ScreenCapture.swift`, `NativeSfuPublisher.swift` через C ABI;
  `--features apm,sfu` во всех сборочных скриптах macOS);
- **Windows** — WGC → D3D11 VideoProcessor (NV12 размера слоя) → H.264 Media Foundation
  (`media/h264_mf.rs`: сначала аппаратные асинхронные MFT, иначе `CLSID_MSH264EncoderMFT`;
  поток на слой, кадр, который поток не успел взять, заменяется новым), издатель — Rust
  напрямую (`media/screen.rs` → `SfuSession`, фичи ядра `apm, sfu` в `apps/windows/Cargo.toml`).
  Странице — NV12 слоя превью. Неподвижный экран WGC не шлёт — раз в секунду слоям
  повторяется последний кадр. Размер слоёв задан при старте: окно сменило пропорции —
  картинка вписывается с чёрными полями (`letterbox_rect`), не растягивается. Метка кадра —
  из выхода кодировщика (у асинхронного MFT выход приходит на кадр позже). Поток
  кодировщика слоя умер (и программный запасной тоже) — странице `closed`/`encoder_failed`;
- **Android** — один VirtualDisplay → SurfaceTexture → OpenGL ES рисует кадр во входные
  поверхности MediaCodec каждого слоя (`ScreenSfuLayers.kt`: с Android 14 второй
  `createVirtualDisplay` на тот же MediaProjection запрещён), издатель — JNI
  (`ZaliSfuNative.kt` ↔ модуль `android` в `sfu_publisher.rs`, ядро — `--features android,sfu`
  в `build_android_core.sh`). Слои не поднялись (кодировщиков меньше, чем слоёв, нет
  EGL) — прежний один кодировщик и `sfuError` в `started`. Стороны слоёв кратны 16 и
  округлены независимо — кадр вписывается в слой с полями (`viewport`). Слой на паузе —
  `PARAMETER_KEY_SUSPEND` (иначе повторы `KEY_REPEAT_PREVIOUS_FRAME_AFTER` кодировались бы
  впустую).

- **Сигналинг ведёт страница** (`voice_sfu.js` → `startVoiceNativeSfuScreen`):
  `start` экрана с `options.sfu` (слои q/h/f: `scale`, `fps`, `bpp`, `minBps`/`maxBps`,
  `maxSide`, `previewLayer`, `startBitrate` — `voiceNativeSfuScreenSpec`) → ответ
  `started` несёт `sfu: {sdp, mid, layers}` → страница шлёт `voice_sfu_publish` со
  `slot: "native"` → ответ сервера с тем же `slot` → `MEDIA_REQUEST op: 'sfu_answer'`.
  У участника на сервере два издателя: страница (камера, звук экрана) и `native_publisher`;
  `voice_sfu_unpublish {slot: 'native'}` снимает второй (`voice_sfu_leave`/`unpublish` —
  только с устройства, держащего звонок). Ошибка нативного слота (`voice_sfu_error` с
  `slot: 'native'`, напр. `bad_offer`) откатывает только экран — без неё страница сочла бы
  SFU недоступным и увела всю комнату в mesh. События издателя приходят
  странице как `media_event {event: 'sfu', stream, sfu}` (`connected`, `bitrates`,
  `stats`, `keyframe`, `closed`).
- **Бюджет слоёв считает ядро** по оценке TWCC (0,9 × оценки снизу вверх, гистерезис
  60 %/35 %), событие `bitrates` → `ScreenCapture.setLayerBitrates`: 0 — слой не кодируется,
  возврат — с ключевого кадра. Превью у себя — кадры слоя `previewLayer` (h); на паузе
  его кодировщик работает для страницы, а ядро такие кадры в сеть не пускает.
- **Ключевые кадры ведёт ядро:** при подключении, после обрыва ICE и при возврате слоя из
  паузы оно само шлёт `keyframe` и до ключевого кадра слоя разностные выбрасывает
  (`need_key`) — иначе зритель получал кашу до своего PLI.
- **Кодек — один на демонстрацию (с 2026-11-24, до этого только H.264).** Страница шлёт в
  `options.sfu.codecs` кодеки, которые декодируют все в комнате, лучший первым
  (`voiceNativeSfuScreenCodecs`: AV1, H265, затем всегда H264), и `previewDecode` — что сама
  декодирует через WebCodecs. Оболочка берёт первый, для которого есть АППАРАТНЫЙ кодировщик
  (macOS — `VideoCodecKind.hardwareEncodeAvailable`, AV1 у VideoToolbox нет; Windows — MFT
  нужного подтипа, иначе следующий кодек; Android — `hardwareEncoderAvailable`), а macOS и
  Android — ещё и только из `previewDecode` (их превью — слой, сжатый тем же кодеком;
  Windows шлёт превью NV12). Выбор — в `started.sfu.codec` и `PublisherConfig::codec`: оффер
  издателя содержит только этот кодек. Пришёл зритель, который его не декодирует, —
  `restartVoiceScreenShare('native-sfu-codec')`, выбор заново. Стенд: `CODEC=H265|AV1` у
  `native_pub.mjs` (слои — `ffmpeg -c:v hevc_videotoolbox -f hevc` / `libsvtav1 … .ivf`);
  2026-11-24: H.265 1080p60 ~6 Мбит/с и AV1 ~5 против ~12 у H.264 на том же материале,
  зрители Chromium и WebKit (H.265), 0 фризов. Живые оболочки с H.265/AV1 не проверены.
- **Ограничения первой версии:** только UDP (без ICE-TCP), звук экрана
  по-прежнему со страницы. Сбой издателя (`closed` не `local`, нет ответа 10 с) —
  `restartVoiceScreenShare` обычным путём; после двух сбоев за звонок — только старый путь.
  Комната ушла в mesh — демонстрация перезапускается. **Android не перезапускает**
  (`inPlace`): новый захват — новое системное окно согласия посреди звонка. Страница
  снимает слот `native`, публикует дорожку превью сама (`fallbackVoiceNativeSfuScreenInPlace`)
  и шлёт оболочке `op: 'sfu_fallback'` — остальные слои встают, издатель закрывается.
- **Ловушка (найдена 2026-11-22):** цикл издателя не должен спать на сокете, когда срок
  str0m уже наступил — пейсер выпускает по пакету и сразу просит новый таймаут. С
  минимальным ожиданием 1 мс выходил потолок ~900 пакетов/с: при трёх слоях верхний
  1080p60 копил очередь и доходил на 50 к/с, а оценка канала застревала на ~10 Мбит/с.
- **Стенд без оболочки:** `core/examples/sfu_pub_file.rs` (готовые Annex B-слои) +
  `scripts/voice_doctor/sfu_e2e/native_pub.mjs` (страница A ретранслирует сигналинг
  настоящим кодом, B — зритель). Прогон 2026-11-22: q 480×270@30, h 960×540@60,
  f 1080p60 4,5 Мбит/с — у зрителя 60 к/с без потерь и фризов; сервер считает кадры и
  разрывы по слоям (`screen/f:4560k/600f/0gap`). В самом приложении не проверено.
- **Windows и Android на устройствах не запускались** (2026-11-22): Windows проверен только
  кросс-сборкой (`cargo xwin check`), Android — сборкой APK; эмулятора и телефона не было.
  Первым делом на живом железе смотреть журнал: `media screen sfu layer N …` (какой
  кодировщик — `hw`/`sw`) и `sfu_layers` в статистике экрана (Windows), `ZaliScreen` в logcat.

## Обработка звука микрофона

`core/src/audio_processing.rs`: `VoiceProcessor` (Rust, Windows) / `zali_apm_*` (C ABI,
macOS через `CoreBridge.h`). 48 кГц моно f32; блоки любой длины. Опорный сигнал —
то, что сейчас играет: macOS — Core Audio process tap (macOS 14.2+, global tap,
`NSAudioCaptureUsageDescription`; без пригушения и без пересборки вывода — проверено);
Windows — WASAPI loopback устройства вывода по умолчанию. Нет опорного сигнала (macOS 13,
отказ в доступе) — AEC без него ничего не вычитает, NS и AGC работают.
Конвейер выбран стендом против C++ AEC3 из WebRTC — подробности в шапке модуля; пороги в
тестах — от измерений с запасом, не придуманные.

**Опорный сигнал и микрофон склеиваются по меткам времени** (`push_render_at` /
`process_capture_at`, `zali_apm_*_at`; с 2026-11-24). AEC3 ищет эхо только позже опорного
сигнала, а тап / loopback приходят из своего потока и опаздывают к обработчику на 10–40 мс.
Без меток опоздание на 5 мс роняет ERLE с 52 до 25 дБ, на 40 мс — до 6 дБ (стенд
`late_reference_is_aligned_by_timestamps`). Так и было во всех живых звонках до этого:
`erle_db` 0,2–9, `delay_ms=0` на Windows. Метки — время первого отсчёта на одних часах:
macOS — `mHostTime` входа IOProc тапа и обратного вызова AUHAL (`MediaClock.nanos`);
Windows — QPC из `GetBuffer` (`WasapiCapture::read` её возвращает). Кадр микрофона уходит в
AEC3 только после опорного до своего конца, но ждёт не дольше 120 мс (`MAX_HOLD_NS`). Если
опорного нет дольше 120 мс (`STALL_NS`; WASAPI loopback в тишине пакетов не шлёт), вместо
него идут нули и микрофон не ждёт. Опорный теперь только копится в `push_render_at`, а в
AEC3 подаётся на потоке микрофона. **Не возвращать** `push_render` без меток в оболочки:
без меток остаётся только для стенда.

**Затвор по VAD после AGC** (`SpeechGate`, с 2026-11-24). RNNoise хорошо снимает ровный
шум (15–26 дБ), но резкие шумы (клавиатура, щелчки мыши, стук) пропускает почти целиком
(4–5 дБ). AGC при тихой речи поднимал их выше исходного уровня — отсюда жалоба «все шумы
слышны очень сильно». Затвор глушит паузы между фразами до −40 дБ. Как устроен:
- **Открытие.** По VAD RNNoise два кадра подряд. Выход RNNoise отстаёт на кадр, поэтому
  VAD следующего кадра уже известен, и задержка не добавляется.
- **Заранее, до VAD.** VAD узнаёт начало фразы под шумом лишь через 2–3 кадра. Поэтому
  затвор открывается раньше, по скачку уровня, сразу по двум сигналам: на выходе RNNoise
  и на входе. Подъём должен держаться в следующем кадре, а энергия не должна сидеть в
  одной четверти кадра: так ведёт себя щелчок.
- **Удержание** 300 мс. Открывается за 1 мс, закрывается за ~150 мс.
- **Глубина** зависит от того, насколько речь громче шума: от ≤ 10 дБ (затвор выключен,
  под сильным шумом он резал бы начала слов) до ≥ 20 дБ (−40 дБ).

Стенд `keyboard_clicks_between_phrases_are_muted`: щелчки в паузах −43 дБ; при тихой речи
с AGC — −40 дБ (без затвора было +0 дБ). Слабое место: щелчок на 20 дБ громче голоса
RNNoise иногда принимает за речь, и тогда затвор открывается.

Захват: macOS — AUHAL только на вход, **без** VoiceProcessingIO (никакого
`kAudioUnitSubType_VoiceProcessingIO`, никакого `setVoiceProcessingEnabled`); Windows —
WASAPI shared, роль `eConsole` (режим «связь» включил бы системное приглушение).

## macOS: ICE без getUserMedia

Пока страница не получила доступ к микрофону/камере через движок, WebKit прячет
локальные адреса за mDNS (`….local`) — прямые соединения в LAN ломаются. Оболочка
выключает фильтр: `WKPreferences` `_setICECandidateFilteringEnabled:false` (проверено
2026-11-12 на macOS 27 — появились настоящие адреса).
