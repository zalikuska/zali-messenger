# Почта: привязка к аккаунту, сброс пароля, почтовый сервер

Сервер умеет отправлять письма сам — отдельный почтовый сервис для этого не нужен.
Письма нужны для двух вещей:

- **привязка почты** к аккаунту — при регистрации и в Настройках → «Почта»; адрес
  подтверждается шестизначным кодом из письма;
- **сброс забытого пароля** — «Забыли пароль?» на экране входа: логин или почта →
  код из письма → новый пароль.

Код — `server/src/account_email.rs` (эндпоинты), `server/src/mailer.rs` (доставка),
`server/src/mail_templates.rs` (письма), клиент — `web/src/interface/account_email.js`.

## Как устроено для человека

1. Регистрация: логин, почта (необязательна), пароль и его повтор.
2. После «Создать аккаунт» — экран ввода кода. Код действует 15 минут, на него 5 попыток,
   повторная отправка — не чаще раза в минуту.
3. «Пропустить» (или почта не указана) — экран «Оставить аккаунт без почты?»: без неё
   забытый пароль не восстановить. Кнопка отказа включается только через 5 секунд.
4. Почту можно сменить в настройках — с текущим паролем; на прежний адрес уходит
   уведомление о смене.
5. Сброс пароля завершает все сеансы на всех устройствах и **удаляет облачный vault**:
   он зашифрован старым паролем, открыть его больше нечем. Переписки возвращаются с
   других устройств аккаунта и через собеседников: правой кнопкой по собеседнику →
   «Восстановить переписку» (`server/src/history_recovery.rs`) — запрос ждёт, пока
   собеседник появится в сети, и его приложение само присылает ключи.

## API

| Метод и путь | Вход | Что делает |
|---|---|---|
| `GET /api/auth/email/config` | — | `enabled`, длина и срок кода. Клиент по нему решает, показывать ли почту |
| `GET /api/auth/email` | токен | подтверждённая почта и незавершённая привязка |
| `POST /api/auth/email` | токен, `{email, password}` | начать привязку/смену: письмо с кодом |
| `POST /api/auth/email/resend` | токен | новый код на тот же адрес |
| `POST /api/auth/email/confirm` | токен, `{code}` | подтвердить |
| `DELETE /api/auth/email/pending` | токен | отказаться от незавершённой привязки |
| `POST /api/auth/password-reset` | `{login}` | письмо с кодом сброса; ответ всегда одинаковый |
| `POST /api/auth/password-reset/verify` | `{login, code}` | код → одноразовый `resetToken` (10 минут) |
| `POST /api/auth/password-reset/complete` | `{resetToken, newPassword}` | новый пароль и вход |

## Безопасность

- В `users.email` — только подтверждённый адрес; один адрес — один аккаунт. Что адрес
  занят, узнаёт только тот, кто ввёл код из этого ящика.
- Код хранится HMAC-отпечатком (ключ выводится из `JWT_SECRET`), сравнение — за
  постоянное время. 5 неверных попыток сжигают код.
- Лимиты писем (в базе, переживают перезапуск): не больше 5 в час на аккаунт и на адрес,
  повтор не чаще раза в минуту, не больше 20 запросов сброса в час с одного IP.
- Сброс не выдаёт, есть ли такой аккаунт и есть ли у него почта: одинаковый мгновенный
  ответ (поиск и письмо — в фоне), один и тот же ответ на неверный, устаревший и
  сгоревший код.
- Привязка и смена почты требуют текущего пароля — украденный токен не перенесёт
  восстановление доступа на чужой ящик. Смена почты гасит незавершённый сброс.
- В письмах нет ссылок — только код. Коды и токены не пишутся в лог, адреса — маской.
- Прямая доставка не ходит на внутренние адреса: MX чужого домена, указывающий на
  127.0.0.1 или частную сеть, пропускается.

## Режимы отправки

`MAIL_TRANSPORT`:

| Значение | Что делает | По умолчанию |
|---|---|---|
| `direct` | сам доставляет на MX получателя (порт 25, STARTTLS), подписывает DKIM | — |
| `smtp` | отдаёт SMTP-relay с логином: STARTTLS 587 или TLS 465 | — |
| `file` | пишет `.eml`, HTML-превью и `.json` в `MAIL_OUTBOX_DIR` | debug-сборка |
| `off` | почта выключена, эндпоинты отвечают 503 | релиз |

Ошибка настройки (нет `MAIL_FROM`, битый DKIM-ключ, relay без шифрования не на
loopback) выключает почту целиком с ошибкой в логе — лучше никаких писем, чем письма в
спам. Очередь — в памяти, повторы на временных ошибках через 30 с, 2, 5 и 10 минут.

Переменные — в `.env.example`, раздел «Почта».

## Свой почтовый сервер (`direct`)

1. **Порт 25.** Многие хостеры закрывают исходящий 25-й порт — без него прямая доставка
   невозможна (`zali_server mail check` проверит). Тогда — `smtp` через провайдера.
2. **PTR.** Обратная запись адреса сервера должна указывать на имя из `MAIL_HELO_NAME`,
   а это имя — обратно на адрес. Настраивается в панели хостера.
3. **DKIM-ключ:**

   ```bash
   zali_server mail dkim-keygen --selector zali --domain example.org --out /etc/zali/dkim.pem
   ```

   Команда печатает готовую TXT-запись `zali._domainkey.example.org`.
4. **DNS домена отправителя:**

   | Запись | Значение |
   |---|---|
   | `example.org TXT` | `v=spf1 ip4:<адрес сервера> -all` |
   | `zali._domainkey.example.org TXT` | из вывода `dkim-keygen` |
   | `_dmarc.example.org TXT` | `v=DMARC1; p=quarantine; adkim=s; aspf=s` |

5. **Окружение:** `MAIL_TRANSPORT=direct`, `MAIL_FROM`, `MAIL_HELO_NAME`, `DKIM_SELECTOR`,
   `DKIM_PRIVATE_KEY_FILE`. Ключ — `0600`, владелец — пользователь сервиса.
6. **Проверка:**

   ```bash
   zali_server mail check
   ```

   ```bash
   zali_server mail test you@gmail.com
   ```

   В заголовках пришедшего письма должны быть `spf=pass`, `dkim=pass`, `dmarc=pass`.

Вёрстку писем можно посмотреть без отправки: `zali_server mail preview dist/mail-preview`.
