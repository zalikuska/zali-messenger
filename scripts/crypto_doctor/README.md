# crypto-doctor

Проверки шифрования и — главное — **синхронизации ключей разговоров**. Цель та же,
что у `voice_doctor`: ловить состояние, в котором всё «работает», а сообщение не
читается. Инвариант здесь не «ключ есть» (ключи были во всех сломанных состояниях,
иногда 16 штук), а:

> любое отправленное сообщение должно остаться расшифровываемым на **каждом**
> устройстве **каждого** участника

```bash
./scripts/crypto_doctor/run.sh             # JS-слои (быстро, годится в CI)
./scripts/crypto_doctor/run.sh --archive   # + Rust-тесты формата .zali
./scripts/crypto_doctor/run.sh --all
```

## Слои

### 1. `check_source.mjs` — инварианты исходника
Правила против конкретных, уже случавшихся форм поломки: ручная «демоция» активного
ключа, ответ на republish только активным ключом, чтение упавшего lookup'а как
«канонического ключа нет», телеметрия расшифровки без восстановления, `Math.random`
рядом с ключевым материалом, запись в хранилище ключей мимо write-lock, отправка
самого ключа вместо отпечатка в registry.

### 2. `check_crypto.mjs` — примитивы (24 проверки)
Настоящий WebCrypto Node. Конверт открывается только своим устройством (и не
открывается ни другим устройством того же аккаунта, ни отправителем); подмена
`recipientDeviceId` не помогает; порча шифротекста ловится AEAD; отпечаток ключа —
это SHA-256, а не ключ; свёртка scope у клиента совпадает с серверной байт в байт;
генератор ключей отказывается работать без CSPRNG (нет отката на `Math.random`);
параметры KDF берутся из кода, а не из присланного пакета.

### 3. `check_keysync.mjs` — синхронизация ключей end-to-end (25 проверок)
Каждое «устройство» — **настоящий** экземпляр `ZaliInterface` в своём sandbox (свой
localStorage, своя ECDH-личность, своё хранилище ключей), подключённый к
симулированному серверу на единственном шве `apiFetch`. Сервер повторяет
`server/src/conversation_keys.rs` (claim по принципу «первый выиграл», force-claim,
проверки участников), выдачу устройств, конверты, cloud vault и — важно —
**WS-пуш `key_republish_request`**, без которого тестировалась бы искалеченная
система.

Сценарии: один ключ на двоих; свёртка scope при разном регистре; второе устройство
аккаунта появляется позже; гонка одновременного открытия чата; канал на трёх
участников; отозванное устройство; нестабильная сеть (10 % и 30 % отказов);
принудительный сброс ключей; 24 рандомизированных прогона с 1–3 устройствами на
аккаунт.

## Что найдено и исправлено этим набором

1. **Принятие канонического ключа теряло предыдущий.** Все три места делали
   `addAltConversationKey(stored, scope, current); stored[scope] = next;` — а
   `addAltConversationKey` в этот момент отказывается, потому что `current` ещё
   является активным ключом. Устройство переставало читать **собственные**
   отправленные сообщения: ровно «перебрано ключей N, ни один не подошёл».
   Исправлено одним `setActiveConversationKey()`.
2. **Ответ на republish присылал только активный ключ** — то есть единственный,
   который у просителя заведомо есть. Теперь отдаются все кандидаты scope.
3. **Sweep `retryPublishConversationKeys` игнорировал исторические ключи**
   (`alt:`-записи — не scope). Если исходная публикация ключа не удалась,
   переспросить его было нельзя никогда.
4. **Провал расшифровки только отправлял телеметрию.** Клиент сообщал «не смог» и
   на этом останавливался; механизм republish запускался лишь когда ключа scope не
   было вовсе. Добавлен `requestKeyRepublishForDecryptFailure` с кулдауном на scope.

## Границы

- Формат `.zali` (AES-256-GCM по чанкам, nonce = `base_nonce[8..12] + chunk_index`
  wrapping-сложением, PBKDF2 210 000) живёт в Rust и Swift — его покрывают
  собственные тесты, они запускаются флагом `--archive`. Swift-зеркало SDK этим
  набором не запускается.
- Проверяется доступность ключа, а не факт расшифровки конкретного шифротекста:
  сообщение моделируется ключом, которым его зашифровали.
- Сервер здесь симулированный. Совпадение с настоящим гарантировано только для
  смоделированных ручек; расхождение в реальном `voice.rs`/`conversation_keys.rs`
  этот набор не увидит.
