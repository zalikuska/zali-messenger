# notify-doctor

Доходит ли уведомление о сообщении до пользователя.

```bash
./scripts/notify_doctor/run.sh
```

Каждый клиент — настоящий `ZaliInterface`, загруженный
`voice_doctor/lib/load_interface.mjs` по `web/src/manifest.json`. Подменены
границы браузера (DOM-отрисовка, звук, персист) и нативный мост, который
записывает каждый `SHOW_NOTIFICATION`. Тест управляет тремя вещами, от которых
зависело, придёт ли уведомление: видимостью документа, фокусом окна и кадрами
анимации.

## Что проверяется и что было сломано (2026-09-13)

| Проверка | Как было |
|---|---|
| открытый чат, окно за другим приложением / свёрнуто / в трее | «чат на экране» не учитывал окно: ни уведомления, ни звука, ни счётчика |
| возврат к окну снимает накопленный счётчик открытого чата | — (появилось вместе с первым пунктом) |
| браузер: видимая, но неактивная вкладка | `showBrowserNotification` срабатывала только в скрытой вкладке |
| догрузка истории нескольких переписок подряд | каждый `loadHistory` отменял недоразобранный предыдущий; новое у всех, кроме последней переписки, не разбиралось никогда |
| догрузка в свёрнутом окне | продолжение разбора ждало `requestAnimationFrame`, а скрытому окну кадров не дают |

### `check_service_worker.mjs` — Web Push (2026-09-13)

Исполняет настоящий `web/service-worker.js` с моделью центра уведомлений (одинаковый
`tag` заменяет запись).

| Проверка | Как было |
|---|---|
| повторный пуш / пуш после локального уведомления вкладки не звенит второй раз | пуш без `tag` и `messageId`: одно сообщение — два уведомления |
| клик ведёт в переписку уведомления | клик просто фокусировал любую вкладку |

В `check_notifications.mjs` к этому добавлена сторона вкладки: `client_presence`
уходит на сервер при изменении и не дублируется. Решение сервера по этим данным
проверяют юнит-тесты `server/src/push.rs`.

Нативная половина второй проблемы — один токен перезагрузки истории на все
переписки в macOS (`WebView.swift`) и Android (`NativeBridge.kt`) — харнессом не
покрыта: это код оболочек, а не веба.
